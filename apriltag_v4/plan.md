# 탑재부 정렬 — 어떻게 풀 것인가 (v4)

2026-09-22 작성 · 2026-09-30 결정 반영(13절 요약, 14절 숫자 대장 — 본문과 다르면 13절이 우선).
어려운 말을 쓰지 않는다. 처음 보는 사람도 읽을 수 있게 쓴다.

숫자에 붙은 표시:
**실측** = 우리가 실제로 잰 값 · **계산** = 실측에서 유도한 값 · **★미측정** = 아직 모르는 값

---

## 1. 무엇을 하는 일인가

지게차가 **탑재부**(차고처럼 생긴 공간)에 스스로 들어가 주차한다.
팔레트에 포크를 꽂는 작업이 아니다 — **포크는 접은 채로 그냥 들어간다.**

```
         탑재부
    ┌──────────────┐
    │           ■  │  ← 태그 (벽에 평평하게. 실증 때는 중앙보다 우측)
    │              │
    └──────────────┘
           ↑
        여기로 들어가야 함
           ↑
          🚜  ← 지게차. 카메라가 앞쪽에 달려 있다
```

### 목표를 좌표로 쓰면

```
        y (좌우)
        ▲
        │
  ──────┼──────────────────────→ x (법선 = 탑재부 중심선)
        │                         ■ 태그
       🚜

목표:  y → 0   그리고   차체 방향 → x축과 평행
```

**둘 다 0 이어야 한다.** 하나만으로는 안 된다:

- y=0 인데 비뚤면 → 들어가면서 옆으로 새고, 차체 모서리가 벽에 닿는다
- 방향만 맞고 y≠0 이면 → 평행하게 빗나간 채로 들어간다

### 얼마나 맞춰야 하나

**조건은 하나다 — 도착했을 때 좌우가 한쪽당 3 cm 안.**
(탑재부 폭 = 지게차 폭 + 6 cm. 실물 값)

태그는 **탑재부 입구**에 있고, 카메라가 태그에서 3.3 m 안으로 들어오면 화면 위로 잘려 안 보인다.
그때 포크 끝은 입구 밖 **1.78 m**(= 3.30 − 1.52). 거기서부터 눈을 감는다.

```
예측 도착 좌우  =  눈 감을 때 좌우  +  1.78 m × sin(방향)
눈 감아도 되나  =  |예측 도착 좌우| + 흔들림  <  30 mm
```

### 방향에는 따로 허용치를 두지 않는다

**방향은 위 식의 드리프트로 이미 들어온다.** 따로 "방향 몇 도" 를 정하면
"좌우가 몇 mm 를 쓴다" 를 가정해야 하는데, 그건 아직 모른다.

**둘은 맞바꿔진다:**

| 좌우가 쓰는 양 | 방향에 남는 몫 |
|---|---|
| 5 mm | 0.80도 |
| 10 mm | 0.64도 |
| 14 mm | 0.52도 |
| 20 mm | 0.32도 |
| 25 mm | 0.16도 |

**이 표의 어느 점을 고를지 미리 정하지 않는다.** 그때 재고 있는 값으로 도착점을 계산해
판정한다(`limits.commit_margin_m`).

```
좌우가 잘 맞아 있으면  →  방향이 좀 비뚤어도 통과
방향이 잘 맞아 있으면  →  좌우가 좀 벗어나도 통과
```

그리고 **비뚤어진 만큼 미리 반대쪽에 서면 상쇄된다**(3-9). 정렬 목표 숫자를 바꾸는 것뿐이라
추가 동작이 없다.

### ★2차(전체 진입)에는 방향 제한이 **따로** 필요하다

**1차는 차가 아직 밖에 있어 벽이 없다.** 포크 끝이 어디 도착하느냐만 중요하다.
**2차는 차 전체가 안으로 들어가므로, 비스듬한 차체가 탑재부 폭을 더 먹는다.**

```
   ┌──────────────────────────────┐
   │  ╱▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔╲        │
   │ ╱      지게차 전체      ╲      │   좌우가 완벽해도
   │╱                        ╲     │   앞은 이쪽 벽, 뒤는 저쪽 벽에 닿는다
   └──────────────────────────────┘

   (안에 든 길이) × sin(방향)  ≤  6 cm        ← 좌우로는 표현이 안 되는 별도 제약
```

| 지게차 길이 | 방향 제한 |
|---|---|
| 3.0 m | 1.15도 |
| 3.5 m | 0.98도 |
| 4.0 m | 0.86도 |

**이건 좌우 판정으로 대체할 수 없다.** 2차로 넘어갈 때 반드시 같이 붙인다 —
`limits.heading_tol_inside_deg(지게차 길이)`. ★지게차 길이는 미측정.

그리고 눈 감는 거리도 1.78 m → 1.78 + 지게차 길이 ≈ **5.3 m** 로 늘어난다.

| 단계 | 눈 감는 거리 | 방향 제한 |
|---|---|---|
| **주행실험** (탑재부 없음) | 1.28 m | 없음 |
| **1차 — 입구 정렬** ★지금 | **1.78 m** | **없음** (좌우 판정에 포함) |
| 2차 — 전체 진입 | ≈ 5.3 m | **(길이)×sin(방향) ≤ 60 mm** |

★**미확정:** 탑재부 깊이 · 지게차 길이 · 탑재부 중앙 대비 태그 좌우 위치.
셋 다 **숫자만 바꾸면 되는 값**이라 코드를 막지 않는다.

## 2. 왜 어려운가

### 문제 1 — 멀리서 잰 값이 흔들린다

8 m 에서 좌우 위치가 **6~14 cm**(최대 41 cm) 씩 흔들렸다(**실측**, 9/7). 허용치가 3 cm 인데.

2026-09-07 실주행이 이것 때문에 실패했다(11회 전부). 없는 오차를 보고 고치려다 좌우로 계속 왔다갔다 했다.

**왜 흔들리나.** 실주행 로그 38개를 다시 재보니:

```
좌우 흔들림  =  거리 × 방향 흔들림

    38개 측정의 비율 중앙값 = 1.00  (범위 0.98~1.03)   ← 실측
```

**좌우가 따로 흔들리는 게 아니다.** 각도를 잘못 재면 그게 거리만큼 증폭돼 좌우로 나타난다.
8 m 에서 각도를 1도 잘못 재면 좌우가 14 cm 틀어진다.

> **가까이 오면 줄지만 사라지지는 않는다.** 9/21 정지 측정(3.68 m, 1459 프레임 — 문제 5-1):
> ```
> 3.7 m 에서   좌우 프레임 sd 39 mm,  방향 0.59도,  화면 위치 0.006도   ← 실측
> 검산: 3.68 m × tan(0.592도) = 38 mm  vs  실제 좌우 39 mm   (일치 — 좌우 = 거리 × 방향)
> ```
> 예산 30 mm 보다 **아직 크다.** 그래서 값마다 "얼마나 믿을 만한가"(σ, 3-6)를 같이 계산한다.
> (이전 판의 "±4 mm" 는 93·82 프레임 두 토막의 값이었다. 1459 프레임 전체로는 39 mm 다.)

### 문제 2 — 명령을 보내도 바로 안 움직이고, 그 시간이 매번 다르다

```
우리 측정(회전):   0.98 ~ 1.50 초   (중앙값 1.32)   ← 실측, n=16
광운대 측 경험:    0.5  ~ 2.0  초
```

"3초 동안 전진해" 같은 명령은 결과를 예측할 수 없다. 어떨 때는 1 m, 어떨 때는 0.6 m 를 간다.

**이게 v4 를 만든 직접적인 이유다.** 지연 시간을 재서 보정하려던 계획이 "매번 다르다" 는 말 한마디로 무너졌다.

### 문제 3 — 멈추라고 해도 바로 안 선다

관성 때문에 더 간다. 회전도 직진도 마찬가지다.

**그런데 그 양이 매번 다르다.** 문제 2 와 같은 성격이다.

```
· 멈출 때의 속도에 따라 다르다      (빨리 돌다 멈추면 더 간다)
· 좌우가 다르다
· 하중 · 노면 · 온도 · 기계 상태로 변한다
· 같은 명령을 반복해도 매번 다르다
```

**그래서 관성을 하나의 숫자로 정하지 않는다.** 재서 박아두면 그 값이 맞는 날이 며칠 없다.
대신 **보수적으로 일찍 멈추고, 멈춘 뒤 다시 재고, 돌면서 배운다**(3-5 · 6절).

> 광운대도 같은 결론이다 — 코드에 `coast is not fitted`(관성은 맞추지 않았다) 라고 적혀 있다.
> 자세한 이유는 6-5.

### 문제 4 — 마지막에는 태그가 안 보인다

카메라가 태그보다 **1.10 m 아래**에 있어서, 가까이 갈수록 태그가 화면 위로 올라가다가
**3.3 m 에서 화면 밖으로 나간다**(**실측**, 9/7 18:14 로그).

```
태그 높이 1.35 m,  카메라 높이 0.25 m  →  높이차 1.10 m     ★둘 다 줄자로 잰 값이 아니다 (5-1 ⑤, 14절 ①)
컬러 1920x1080 세로 화각 43도
     →  (1.10 + 0.15) × 1359 ÷ (571 − 60) = 3.32 m       계산과 실측이 일치
```
태그컷은 계산값이라 config 에 없다(`limits.tag_cut_m`) — 그리고 실행은 아래처럼 프레임마다 다시 잰다.

**태그컷은 실행 중 프레임마다 다시 잰다 (2026-10-01).** 위 3.32 m 는 "피치 0 · 높이차 고정" 의 명목값이다. 오르막·요철·카메라 처짐은
자세가 준 카메라 높이(`Fix.vertical_m` — 위치라 피치와 무관)와 화면에서 실제로 본 윗변 행(`Fix.top_px`)의 차, 곧 카메라 피치로 드러난다:
```
피치   = atan(윗변높이 ÷ 거리) − atan((cy − 윗변행) ÷ fy)          윗변높이 = −vertical + 태그/2
태그컷 = 윗변높이 ÷ tan(여유각 + 피치)                                여유각 = atan((cy − 60) ÷ fy)      (`limits.tag_cut_live_m`)
```
피치 0 이면 위 식과 같다. "도착" = 더 갈 거리(지금 거리 − 이 태그컷) ≤ 앞뒤 허용 — 곧 **윗변이 60 px 띠에 든 것**. 통로·걸음 길이·마지막
다리의 정지 목표(`Decision.to_cut`, run `_look_step`)도 그 순간 값을 쓴다. 요철(짧은 덜컹)은 0.5 초 창이 삼키고 경사(긴 변화)는 창이 따라간다.
실측 대조는 따로 안 한다(before_run 폐지, 2026-10-02) — run 로그의 `컷` 값과 태그를 잃는 순간의 거리를 사후에 견준다. **눈 감은 1.3 m 안에서 바뀌는 경사는 어떤 식으로도 못 본다** (사용자 수용).

그 뒤로는 **눈을 감고** 가야 한다. **눈 감고 가는 거리는 1.78 m** 다:
```
태그 컷 3.30 m (카메라~태그면)  −  포크 끝이 카메라보다 1.52 m 앞  =  1.78 m
```

| 방향 오차 | 1.78 m 가면 좌우로 |
|---|---|
| 0.5도 | 16 mm |
| **1.0도** | **31 mm ✗ 예산 초과** |
| 2.0도 | 62 mm ✗ |

**눈 감기 직전에 방향이 0.5도 안이어야 한다.**

### 문제 5 — 정면에서 자세가 뒤집혀 보일 수 있다

태그는 평평한 종이다. 평평한 것을 정면에서 보면 "왼쪽으로 기울었다" 와 "오른쪽으로 기울었다"
가 화면상 거의 똑같이 보인다. 계산이 엉뚱한 쪽을 고를 수 있다.

```
3.5 m 에서 두 해를 구분 못 하는 프레임 비율 = 14.1 %     ← 실측, n=3465 (9/21)
```

★8 m·5 m 에서는 미측정. 멀수록 나쁠 것으로 보이지만 근거는 없다.

**중요:** 이건 **흔들림이 아니라 치우침**이다. 여러 프레임의 중앙값을 내도 안 잡힌다.
한 번 잘못된 쪽을 고르면 그 창 전체가 같이 틀린다.

> **배치가 조금 도와준다.** 카메라가 태그보다 1.10 m 아래라 **항상 올려다본다.**
> 완전 정면(0도)이 제일 나쁜 조건인데 우리는 절대 0도가 되지 않는다.
> ```
> 8 m → 7.8도      5 m → 12.4도      3.3 m → 18.4도       (계산)
> ```
> **가까울수록 안전해진다.** 다만 8 m 의 7.8도는 충분치 않다.

### 문제 5-1. 실측으로 맞춘 잡음 모델 — **여유 30 mm 를 지금은 못 지킨다**

실제 카메라 없이 태그 네 모서리를 화면에 투영해 잡음을 넣고 다시 자세를 푸는 식으로 돌린 뒤,
**2026-09-21 실차 기록**(`work_dirs/20260921_측정기록.json`, `fake_source:false`, 3.68 m 정지 1459 프레임)과
**2026-09-07 실주행**(v1 `docking_log`, 30프레임 측정 38개)에 맞췄다. 맞춘 값: **모서리 잡음 0.20 px**.

```
9/21 실측 3.68 m 정지 1459 프레임      시뮬(0.20 px)
  좌우 프레임 sd     39.3 mm             39.3 mm
  방향 프레임 sd      0.592도             0.612도
  화면위치 sd        0.0061도            0.0042도
  두 해 모호율        0.0 %               0.0 %
  프레임 지연 L       중앙 21.4 ms (0.9~112.5)      <- 50 ms 가정은 틀렸다
```

**① 좌우 = 거리 x tan(방향 흔들림).** 9/7 38개·9/21 1459프레임 양쪽에서 1~2 % 안으로 맞는다.
좌우를 따로 재는 게 아니라 **방향 오차가 거리만큼 증폭된 것**이다(9/7 결론과 동일).

**② 정면이 최악, 비스듬이 최선 — 실측으로 확인된다.** 9/7 에서 같은 10.9 m, 같은 태그 크기(37~39 px):
```
  정면 부근(tilt 3.4도)   좌우 프레임 sd 288 mm
  비스듬 (tilt 33도)      좌우 프레임 sd  43 mm      <- 6.7 배 낫다
```
시뮬이 아니라 **실측이** 이 효과를 보여준다. 기하가 조건수를 정한다는 뜻이다.

**③ ★잡음이 프레임 간 독립이 아니다 — 평균 내도 거의 안 준다.**
```
  9/21 좌우 잡음 자기상관 lag 1/2/5/10/30 = 0.60 0.60 0.60 0.63 0.61   (안 줄어든다)
  30프레임 평균의 sd = 30.9 mm   (독립이었다면 7.2 mm 여야 한다)
```
느리게 흘러가는 성분이 60 % 다. **"여러 장 평균내면 sigma 가 1/sqrt(n) 로 준다"는 전제는 틀렸다.**
`estimate.py` 가 잔차로 sigma 를 내면 실제보다 4 배 확신하게 된다 — 고쳐야 한다.

**④ 그래서 지금 배치로는 여유 30 mm 를 못 지킨다.** 태그컷 3.3 m 에서 30 cm 태그·정면이면
좌우 sd 32 mm — **여유 전부**다. 평균으로도 31 mm 까지밖에 안 준다.

지렛대는 넷, 전부 3.3 m·30 cm 기준 (시뮬, 0.20 px):
```
  태그를 키운다      30cm 32mm -> 40cm 24mm -> 50cm 19mm -> 60cm 15mm -> 80cm 11mm
  비스듬히 본다      정면 32mm -> 옆 0.6m 24mm -> 1.0m 16mm -> 1.5m 8.6mm -> 2.0m 4.0mm
  더 가까이서 잰다    3.3m 32mm -> 2.5m 14mm -> 2.0m 7.6mm -> 1.5m 3.4mm
  높이차를 키운다     0m 126mm -> 0.5m 50mm -> 0.81m 32mm -> 1.10m 24mm -> 1.50m 19mm
```
**"더 가까이서 잰다" 가 제일 세다.** 그런데 3.3 m 에서 태그가 화면 밖으로 나가니 못 한다 —
그래서 **태그를 낮춰 다는 것**(컷 거리가 줄어든다)과 **근거리 태그 2장**이 대문제 4 의 핵심이다.
비스듬히 보기는 그 다음으로 세고, 움직임 설계와 방향이 같다.

**⑤ 실측된 높이차는 0.81 m 다** (9/21 정지 1459프레임의 |vertical| 중앙 0.806, sd 0.028).
9/7 의 잘 조건된 측정 9개는 1.23 m 를 준다 — **그날그날 다르게 달렸다**는 뜻이다.
config 의 `TAG_HEIGHT_M=1.35 / CAMERA_HEIGHT_M=0.25`(= 1.10 m)는 **어느 실측과도 안 맞는다.**
높이차가 조건수를 지배하므로(위 표: 0.81 m 32 mm vs 1.10 m 24 mm) **내일 줄자로 재야 한다.**

★남은 의문: 9/21 의 다른 런(`20260921_141659_all`)은 3.5 m 에서 모호율 14.1 %(n=3465)인데
여기 쓴 런은 0.0 % 다. 같은 날 같은 거리인데 갈린다 — 배치가 달랐을 가능성이 크다. 확인 필요.

## 3. 어떻게 풀 것인가

핵심 생각 하나로 요약된다:

> **정확하게 움직이려 하지 말고, 조금씩 움직이고 자주 다시 본다.**

지연 시간이 매번 다르니 "정확히 1 m 가기" 는 포기한다. 대신 **짧게 가고 멈춰서 다시 재고,
거기서 다시 계획한다.** 한 번 빗나가도 다음 번에 그 자리에서 새로 계산하므로 **오차가 쌓이지 않는다.**

### 3-1. 전체 흐름

```
① 멀리서 대충 맞추기        태그 값이 못 미더운 거리
   비스듬히 접근해 좌우를 줄인다. 목표는 완벽이 아니라 ±20~30 cm

② 가까이 오면서 정교하게     ← 여기가 핵심
   짧게 가고 → 멈추고 → 돌고 → 다시 계획   (반복. 계산은 가면서도 한다 — 3-4)
   3.3 m 에 닿기 전에 정렬을 끝낸다

③ 태그컷(3.3 m)에 닿으면 진입 조건을 본다 (1절의 식)
   안 되면 고친다 — 방향 회전 · 비켜서기 · 후진(딱 한 번, 최후의 보루). 합계 5회 · 120초 안 (3-9)
   그래도 안 되면 정지 · 사람

④ 마지막 1.78 m 는 눈 감고 직진
```

**①에서 90도 돌아 옆으로 가는 것(사이드스텝)은 반복 전략이 아니다.** v1 은 그걸 매 걸음 반복해 11회 전부 실패했다.
우리는 **처음 한 번, 통로(3-2) 밖에 있을 때만** 쓴다.

### 3-2. 한 걸음이 무엇인가

**한 걸음 = 제자리에서 조금 돌고 + 조금 직진.** 곡선 주행(돌면서 전진)은 하지 않는다.

**이유가 기하에 있다:**
```
제자리 회전  →  방향은 바뀌는데 좌우는 거의 안 바뀐다
직진        →  좌우는 바뀌는데 방향은 안 바뀐다
```
**둘을 동시에 0 으로 만들 수 없다.** 그래서 이런 모양이 된다:

```
  y                 ② 비스듬히 전진 (좌우가 줄어든다)
  ▲      ①돌고 ╱▔▔▔▔▔▔╲ ③다시 돌아 정면
  │         🚜         🚜 → → → → → →  ④ 직진
──┼────────────────────────────────────────→ x
```

한 걸음을 정할 때 **몇 걸음 앞까지 그려본다.** 지금 한 걸음만 보고 고르면
"지금은 좋은데 나중에 막히는" 자리로 갈 수 있기 때문이다:

- 좌우 오차는 줄었는데 **태그가 화면 밖으로 나가버린다**
- 탑재부에 가까워졌는데 **마지막에 돌 공간이 없다**

여러 경로를 그려보고 **끝까지 들어갈 수 있는 경로**만 후보로 삼는다. 그중 제일 빠른 것을 고른다.

**그런데 그 경로를 다 따라가지는 않는다. 첫 걸음만 간다.** 그리고 멈춰서 다시 보고, 처음부터 다시 그린다.

> 체스에서 몇 수 앞을 읽고 한 수만 두는 것과 같다.

#### 통로 — 대각선 한 번으로 들어갈 수 있는 범위 (2026-09-30 결정 4)

대각선으로 가면 태그가 화면 가운데서 옆으로 밀린다. **도착점(태그컷, 법선 위)에 닿는 순간
태그의 화면 위치 β 는 경로각과 같아진다** — 법선 위에 서 있는데 몸은 경로각만큼 비스듬하니까.
그래서 경로각에 상한이 있다:

```
경로각 상한 = 반화각 − atan(태그 반변 ÷ 태그컷) − 가장자리 여유(60 px)
            = 35.1도  −  2.6도  −  2.5도  ≈  30도            (1920x1080. 계산 — limits.py)
```

거리마다 "대각선 하나로 지울 수 있는 좌우" 가 정해진다. 그 안이 **통로**다:

```
통로 반폭(거리) = K × tan(경로각 상한) × (거리 − 태그컷)        K = CORRIDOR_K = 0.8
                = 0.46 × (거리 − 3.3 m)

   8 m → ±2.17 m     5 m → ±0.79 m     4 m → ±0.32 m     3.3 m → 0
```
```
  y
  ▲  ╲                                통로 = 깔때기.  태그컷에서 폭 0 으로 닫힌다
  │    ╲       통로 안 → 대각선 한 번 (3-2 의 한 걸음)
  │      ╲__________________
──┼──────────────────────────── ■ 태그  → x
  │      ╱▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔▔
  │    ╱       통로 밖 → 사이드스텝 한 번 → 그 뒤엔 중간점 계획 (후진은 여기서 안 한다 — 3-9)
  ▼  ╱
     8 m  ←──── 거리 ────→  3.3 m
```
K = 0.8 은 광운대 "lower envelope 의 80 %"(fsm_v4/config.py L31) 와 같은 안전계수다.
상수는 K 하나. 나머지는 **카메라에서 읽은 intrinsics**(run 이 열자마자 읽음, 없으면 D435I_COLOR_REF)로 계산한다.

#### 통로 밖이면 — 사이드스텝 한 번, 그 뒤엔 바로 중간점 계획 (결정 5)

**사이드스텝** (처음 한 번만. 반복하지 않는다):
```
① 태그를 보고 좌우 y 를 읽는다
② 회전 = (±90도 − 지금 방향)     법선 기준 직각. IMU 폐루프. 이때만 90도까지 허용 (안전망 SIDESTEP_ROT_SAFETY_S 30 s)
③ |y| × SIDESTEP_FRACTION(0.5)     **시간 개루프** (forward_timed. byte 67.  시간 = 거리 ÷ fwd_speed + fwd_startup — 1 m 면 4.9 s)
④ 회전 = (0도 − 지금 방향)         다시 법선을 본다
⑤ 다시 재고 계획으로
```
- 방향은 v1 의 `plan_lateral_clear` 규칙(apriltag_v1 control_from_pose.py L29-36): 앞으로 가는 쪽과 뒤로 가는 쪽 중
  **회전이 작은 쪽**. 뒤로는 다리 ≤ 뒤공간(BACK_MAX) 이고 back_speed 를 알 때만.
- 절반만 가는 이유: 멀리서 읽은 y 는 흔들린다(문제 1). 다 믿고 다 가면 반대로 넘어간다.
- 눈 감고 시간으로 가는 유일한 구간이다. 학습하지 않는다. 직진 하드 상한(1.5 m)도 안 건다 — 그건 걸음용이다.
- 90도 회전이 좌우를 크게 움직여도(4-6) 상관없다 — 끝나고 반드시 다시 잰다.
- **딱 한 번이다.** 끝나면 통로 안이든 밖이든 **바로 중간점 계획**(위의 한 걸음)으로 간다. 아직 통로 밖이면 계획기가
  여러 걸음으로 풀어 본다 — 30도 대각선은 통로 경계(K = 0.8)보다 좌우를 빨리 지운다
  (8 m → 3.3 m 사이에 (1 − K) × tan 30도 × 4.7 m ≈ 0.5 m 만큼). 경로가 안 나오면 실패 ⑥(3-10) — 정지 · 사람.

**여기서 후진은 하지 않는다** (결정 6). 후진은 마지막 단계(태그컷 도착 뒤)에서 딱 한 번 쓰는 **최후의 보루**다 — 3-9.
중간점 계획의 후보에도 후진은 없다. 뒤공간(config `BACK_MAX_M` 0.5)은 그때 쓴다.

### 3-3. 한 걸음을 얼마나 크게 잡을 수 있나

**고정값이 아니다. 매번 계산한다.**

```
한 걸음 최대 전진 = 다음 셋 중 제일 작은 것

  ① 좌우 예산:  남은 좌우 여유 ÷ sin(지금 방향 불확실도)
  ② 화각:       태그가 화면 밖으로 안 나가는 최대 전진
  ③ 남은 거리
```

**①이 왜 필요한가** — 직진하는 동안 좌우로 새는 양은 거리에 비례한다:

| 방향 오차 | 1 m 감 | 2 m 감 | 3 m 감 |
|---|---|---|---|
| 0.5도 | 9 mm | 17 mm | 26 mm |
| **1.0도** | 17 mm | **35 mm ✗** | 52 mm ✗ |

방향을 1도 오차로 알고 있으면 **1.7 m 넘게 가면 안 된다.**
거리 자체는 상관없다 — 멈추는 건 아래 3-5 처럼 폐루프라 얼마를 가든 정확히 선다.

**②의 예** — 지금 5 m 인데 태그가 3.3 m 에서 잘리면 **1.7 m 까지만** 갈 수 있다.

config 에는 **안전 상한 하나**만 둔다. 걸음 크기는 코드가 ①②③ 으로 계산한다.

### 3-4. 계산은 늘, 회전 실행만 멈춘 뒤

**"계산" 과 "회전 실행" 을 나눈다** (2026-09-30 결정 7).

| | 언제 | 쓰는 것 |
|---|---|---|
| **계산** (다음에 몇 도 돌고 몇 m 갈까) | **늘** — 정지 중이든 직진 중이든 | 정지 · 직진 프레임 |
| **회전 실행** | **멈춘 뒤에만** 건다 | 회전 중엔 자이로만. 화면 위치 β 는 쓴다 |
| **정지 시점** (지금 멈춰야 하나) | 움직이며 | 직진: 카메라 거리 · 회전: 자이로 |
| **학습** (실제로 얼마나 갔나/돌았나) | 동작이 끝난 뒤 | 정지 전후 |

**직진 중 프레임을 계산에 써도 되는 근거 — 롤링 셔터 계산이다.**

카메라는 화면을 위에서 아래로 한 줄씩 읽는다. 움직이는 중이면 태그의 위쪽과 아래쪽이
서로 다른 순간에 찍힌다.

```
태그 높이 ≈ 116 px (3.5 m),  한 줄 ≈ 31 µs  →  태그 하나 읽는 데 3.6 ms
```

| | 3.6 ms 동안 | 화면에서 | 코너 잡음(0.07 px) 대비 |
|---|---|---|---|
| **전진 0.3 m/s** | 1.1 mm 접근 | **0.04 px** | 절반 → **무시 가능** |
| **회전 7도/s** | 0.025도 회전 | **0.6 px 어긋남** | 8배 → **가짜 각도 0.3도** |

```
전진 중                       회전 중
┌──────┐                     ┌──────┐
│  ■   │  똑바로 찍힘          │  ▟▙  │  위아래가 어긋나 찍힘
└──────┘                     └──────┘  → "비스듬히 서 있다" 로 오해
```

**그래서:**
```
전진 중   →  거리·좌우·방향 전부 계산에 쓴다 (0.04 px 는 코너 잡음 아래)
회전 중   →  카메라 자세는 안 믿는다. 자이로만. 화면 위치 β 는 쓴다 (모양이 아니라 위치라 왜곡이 없다)
회전 실행 →  멈춘 뒤에만. 직진이 끝나고 조용해지면(1.0 s 전 값과 비교, 3-5) 건다
```
run 이 출발 뒤 정지 60초로 σ 를 잰다(3-6, 2026-10-02). 직진 σ 는 지금 안 잰다 — 정지 것을 쓴다(Noise.sigma_drive_* 자리는 남겨 뒀다).

★한 줄 읽는 시간(31 µs)은 추정값이다. 실측 목록에 있다.

> **우리가 광운대보다 유리한 점:** 검출 지연이 **22 ms**(실측) 대 그쪽 **170 ms**.
> 0.3 m/s 로 갈 때 낡은 정보의 양이 **7 mm 대 51 mm** 다.
> 그쪽은 동작마다 2초씩 서지만, 우리는 **"조용해졌나" 를 보고 바로 간다**(상한만 둔다).
> 걸음마다 1초씩 아끼면 10걸음에 10초다.

### 3-5. 한 걸음을 어떻게 실행하나 — 시계를 안 본다

"몇 초 동안 전진" 이 아니라 **"남은 거리를 보면서 간다."**

```
매 순간:
  카메라로 남은 거리를 잰다
  지금 속도로 "멈추라고 하면 어디에 설지" 계산한다
  그 자리가 목표에 닿으면  →  멈춤
```

**출발이 언제 걸렸는지 몰라도 된다.** 지연이 0.5초든 2초든 상관없다.

**속도를 어떻게 아나:**
```
전진 중 매 프레임의 (시각, 남은거리) 를 직선으로 맞춘다  →  기울기 = 속도
   한 프레임이 튀어도 휩쓸리지 않게 보수적인 쪽(느린 쪽)을 쓴다
   창이 이만큼은 차야 기울기를 믿는다:  FIT_MIN_SPAN = 3 × 거리잡음(Look.sigma_m) ÷ 정속(learner.fwd_speed)
                                       39 mm · 0.29 m/s 면 0.40 s.  상수가 아니다 (결정 9)
멎음 판정은 옆 프레임이 아니라 **1.0 s(SETTLE_SPAN_S) 전 값과** 비교한다 — 미끄러지는 중엔 옆 프레임끼리 잡음 아래다
```
눈 감고 시간으로 가는 `forward_timed()` 는 **사이드스텝 전용**이다(3-2). 학습하지 않는다.

**측정 나이를 빼준다.** 자이로는 "지금" 을 알려주지만 **카메라는 "조금 전" 을 알려준다.**
```
노출 ──①── 도착 ──②── 검출 끝 ──③── 다음 프레임
       모른다     21.8 ms       최대 33 ms
                 (실측)        (프레임 간격)
```
②③ 은 **매 프레임 실제로 잰다.** ①은 **따로 안 잰다** — τ 와 합쳐져 자동으로 학습된다(4-10).

**안전장치 셋** (광운대 `motion.py` L51-73 의 구조):
```
· 속도 상한       한 프레임 튐이 가짜 전진으로 변하지 않게
· 예측 전진량 절대 상한
· 최소 진행 게이트  실제로 목표의 일정 비율을 간 뒤에만 예측 정지 허용
```

**그리고 무조건 멈추는 상한 둘:** 거리 상한, 시간 상한.
(9절의 "시간으로 거리를 맞추지 않는다" 와 충돌하지 않는다 — **거리를 맞추는 게 아니라 멈추는 용도**다.)

### 3-6. 못 믿을 때는 **고치지 않는다** (가만히 있는 게 아니다)

2026-09-07 실패를 막는 규칙이다. 값을 잴 때마다 **"이 값이 얼마나 믿을 만한지"도 같이 계산**한다.

| 판정 | 조건 | 행동 |
|---|---|---|
| 움직인다 | 오차가 흔들림보다 확실히 크다 (**2배**) | 고친다 |
| 됐다 | 오차가 허용치보다 확실히 작다 | 다음 단계로 |
| **모르겠다** | 그 사이 | **좌우를 고치지 않는다. 대신 아래를 한다** |

**"모르겠다" 가 교착이 되지 않게 — 항상 할 일이 있다:**
```
① 전진할 수 있으면 전진한다     ←  가까이 가면 저절로 정확해진다
② 전진도 못 하면 더 오래 본다   ←  떨림만 준다. 밀림(아래 σ)은 안 준다 — 그래서 ①이 먼저다
③ 그래도 안 되면 기준을 낮춘다  ←  2배 → 1.5배
④ 그래도 안 되면 사람을 부른다
```

**교착이 잘 안 생기는 이유:** "모르겠다" 는 멀 때 생기는데, 멀면 전진할 데가 있다(①).
가까워도 안 나온다는 보장은 없다 — 3.7 m 프레임 sd 가 39 mm 다(9/21). 그래서 ③④가 있다.

#### "흔들림" σ 를 어떻게 정하나 (2026-09-30 결정 8 — `estimate.py`)

프레임을 모아 평균내도 잡음이 1/√n 로 안 준다(문제 5-1 ③: 자기상관 0.6). 그래서 σ 를 둘로 나눈다:

```
σ = √( 밀림² + 떨림² )

밀림   run 이 출발 뒤 그 자리에서 정지 60초(`SIGMA_STILL_S`)로 잰 "0.5초 창 평균의 흔들림"
       → Noise.sigma_drift_lateral_m · sigma_drift_heading_deg  (@ sigma_ref_distance_m) — estimate.baseline_from_rows
       다른 거리에서는 비례로:  방향 σ ∝ 거리,  좌우 σ ∝ 거리²      (좌우 = 거리 × 방향, 방향 잡음 ∝ 거리)
떨림   지금 창(0.5 s)의 직선 잔차 sd ÷ √n  (창 끝에서 읽는 지렛대 포함)
```
밀림은 프레임을 더 모아도 안 줄고, 떨림은 준다. 잔차 σ 는 진단으로 따로 남긴다.
`SIGMA_FLOOR_M/DEG` 는 없앤다 — 밀림이 그 역할을 실측값으로 한다.

**뒤집힘(두 PnP 해)은 프레임 한 장씩 뺀다.** 광운대 팔레트는 평면이 아니라 뒤집힘이 없지만
우리 태그는 3.5 m 에서 14 %(9/21)다:
```
angle_ok=False 인 프레임  →  좌우·방향 트랙에서 제외.  화면 위치 β · 거리는 넣는다 (뒤집혀도 멀쩡한 값)
깨끗한 프레임 < MIN_N(3)  →  uncertain("few")            창의 절반 규칙(AMBIG_FRAC)은 없앤다
측정 나이 < −1 ms         →  why="clock"                 시계가 섞인 것. 조용히 넘기지 않는다 (4-10)
```

### 3-7. 멀리서는 각도 대신 화면 위치를 쓴다

문제 1·5 때문에 멀리서는 각도를 못 쓴다. 대신 **화면에서 태그가 어느 쪽에 보이는지**를 쓴다.

```
태그 중심이 화면 중앙에서 몇 픽셀 벗어났나  →  몇 도 벗어났나
```

- 픽셀 위치는 **그냥 보이는 것**이라 계산이 개입하지 않는다 → 뒤집힘 문제가 없다
- 0.3 픽셀 = **0.013도**(계산). 9/21 실측 흔들림 **0.006도**(1459 프레임)

**멀리서는 태그를 화면 중앙에 두고 접근**하고, 가까워져 각도가 믿을 만해지면 그때 좌우를 맞춘다.

### 3-8. 태그를 놓쳤을 때 — 끊어서 한 바퀴

```
① 마지막에 보이던 쪽으로  오른쪽 끝으로 사라졌으면 오른쪽부터
② 50도씩 돌고 멈춰서 확인  가로 화각 70도라 50도씩이면 겹쳐서 안 놓친다
                          한 바퀴 = 8번,  약 40초
③ 반대 방향으로 한 바퀴 더
④ 그래도 없으면 사람을 부른다

**여기서 후진은 하지 않는다** — 후진은 마지막 단계에서 진입 조건이 안 될 때 딱 한 번뿐이다 (3-9, 결정 ⑥).
관성으로 지나쳐 화면 위로 나간 경우도 돌면서 다시 잡는다.
```

**연속으로 360도 돌리지 않고 끊는 이유:**
```
· 도는 동안은 눈을 감은 셈이라 태그를 지나칠 수 있다
· 회전중심이 카메라 앞 ~1.5 m 라 한 바퀴 돌면 반지름 1.5 m 원을 그린다
     →  돌기 전에 주변 여유를 확인한다
```

찾은 뒤에는 **그 자리에서 처음부터 다시 계획한다.** 위치가 많이 달라져 있어도 상관없다.

### 3-10. 실패했을 때

**실패는 일곱 가지다:**
```
① 시간 초과 (300초)            ⑤ CAN 끊김 (TXACK 없음 / 버스 오류)
② 태그를 영영 못 찾음 (3-8 다 돌음)  ⑥ 갈 수 있는 경로가 없음
③ "모르겠다" 가 안 풀림 (3-6 ④)     ⑦ 마지막 단계에서 보정 5회 또는 120초를 다 썼는데 허용치 밖 (3-9)
④ 자이로가 죽음
```

**처음엔 전부 "멈추고 사람 부르기" 로 통일한다.**
```
자동으로 후진해 재시도  →  위험이 늘고, 왜 실패했는지 못 배운다
멈추고 기록을 남긴다    →  이력을 보고 나중에 자동 복구를 붙인다
```
정지 이유는 정해진 목록에서만 고르고(6-6 ④), 세션 요약의 `outcome.fail_reason` 에 남는다.

### 3-9. 마지막 구간 — 진입 판정, 고치기, 후진은 최후의 보루

태그가 3.3 m 에서 안 보이게 되므로 **그 전에 정렬을 끝낸다.** 그다음 1.78 m 는 그대로 직진한다.

**마지막에 필요한 건 거리 정확도가 아니라 방향 정확도다.**

**그리고 방향 오차를 좌우 위치로 일부 상쇄할 수 있다:**
```
눈 감기 직전에 방향과 그 σ(3-6)를 같이 재니까, 얼마나 밀릴지 안다
   "0.3도 기울었다 → 1.78 m 가면 9 mm 밀리겠다"  →  9 mm 반대쪽에 서서 출발     (limits.offset_target_m)
```
다만 **완전히는 상쇄되지 않는다** — 비스듬한 채로 들어가면 차체가 더 넓은 폭을 차지한다(1절).

#### 태그컷에 닿았는데 진입 조건이 안 되면 (2026-09-30 결정 6)

```
중간점을 다 갔다 (태그컷 도착 = 마지막 단계 진입. 여기서 시계가 돈다)
  → 진입 여유 = 3 cm − (|예측 도착 좌우| + σ_좌우 + 1.78 m × sin σ_방향)      limits.commit_margin_m
       양수  →  눈 감고 간다
       음수  →  고친다:  방향 회전 (하한 위) · 비켜서기 (하한 아래, 위 식) · 후진 (딱 한 번, 아래)
  → 고치는 동작 합계 ≤ MAX_CORRECTIONS(5)   그리고   마지막 단계 진입 후 FINE_TIME_LIMIT_S(120)
       둘은 **같은 구간**을 횟수와 시간으로 이중으로 재는 것. 먼저 걸리는 쪽에서 정지 · 사람
```

**후진은 최후의 보루다 — 마지막 단계에서 한 번만.** 중간점 계획의 후보에 후진은 없고, 사이드스텝 직후에도 없다(3-2).
```
언제    남은 좌우가 2σ 보다 클 때만.  그 안이면 진짜 오차인지 잡음인지 모르니 물러나도 소용없다 → 바로 정지 · 사람
얼마나  후진량 = clamp( max( 남은 좌우 ÷ (K × tan 경로각상한),  배운 최소걸음 ),  0,  뒤공간 )
          남은 좌우 ÷ (K × tan 30도) = 2.165 × 남은 좌우   ← 통로 반폭 식(3-2)을 거리로 푼 것. limits 가 계산, 상수로 안 박는다
          최소걸음 = 속도 × 관성시간 (learner 가 배운 fwd_speed · τ)   ← 이보다 짧은 걸음은 관성이 다 먹는다
          뒤공간 = config BACK_MAX_M 0.5 (현장 값, 묻지 않는다)
          필요량 > 뒤공간  →  정지 · 사람
그 뒤    다시 중간점 계획 → 그래도 안 되면 정지 · 사람
```
예: 태그컷에서 좌우 5 cm 가 남았고 σ 가 2 cm 면(5 > 2×2 ✓) 필요량 = 2.165 × 0.05 = 0.11 m. 9/7 실측 정지 관성이 12~14 cm 라
최소걸음이 이보다 크면 그쪽을 쓴다. 물러난 자리에서 통로 반폭이 딱 남은 좌우가 된다 — 깔때기가 그만큼 넓어진다.
**0.5 는 상한이 아니라 "뒤공간을 안 쟀을 때의 대체값"이다** — 현장에서 잰 뒤공간이 우선한다.

## 4. 제자리 회전

회전은 우리 오차의 제일 큰 원인이라 따로 적는다.

### 4-1. 누가 목표를 정하고 누가 실행하나

```
목표 각도  →  카메라가 정한다      (태그가 절대 기준)
실행       →  자이로가 본다        (200 Hz. 회전 중 태그 자세는 못 믿는다 — 3-4)
교차 확인  →  화면 위치(β)         (모양이 아니라 위치라 롤링 셔터에 강하다)
최종 확인  →  멈춘 뒤 카메라
```

**자이로와 β 가 어긋나면** 멈추고 정지 상태에서 다시 잰다. 자이로 드리프트·이상을 이렇게 잡는다.

자이로는 **"영점 선언 후 몇 도 돌았나"** 만 안다(자력계가 없다). 그래서 짧은 구간에서만 쓰고,
매번 태그로 기준을 다시 잡는다.

> **광운대도 같은 자이로를 갖고 있다**(`imu_stream.py`, 같은 D435i). 그런데 **눈이 먼 구간에만** 쓴다 —
> 90도 돌아 옆으로 가는 동안 팔레트가 안 보이기 때문이다(상태 이름이 `COARSE_BLIND_STATES`).
> 정밀 회전에서는 팔레트가 계속 보이고 **허용치가 20도**라 카메라로 충분했다.
> **"못 쓴 게" 아니라 "쓸 필요가 없었다".**
>
> 우리가 써야 하는 이유는 둘이다:
> ```
> ① 허용치가 0.5도다      카메라 값이 회전 중 2도 낡는다 → 못 쓴다
> ② 태그가 1.10 m 위에 있다  회전하면 화면 밖으로 나갈 수 있고, 롤링 셔터가 자세를 0.3도 왜곡한다
> ```

### 4-2. 언제 멈추나 — 규칙 하나

```
회전:  남은각   ≤ ω × (   0    + τ + 판정주기÷2 ) + 잔여보정
직진:  남은거리 ≤ v × ( 측정나이 + τ + 판정주기÷2 ) + 잔여보정
                         ↑         ↑       ↑          ↑
                    카메라는 낡았다  배운 값  지금 잰 값   조건별로 배운 작은 값
                    자이로는 0
```

| 항 | 무엇 | 어떻게 구하나 | 어디에 저장 |
|---|---|---|---|
| **τ** | 관성 시간 | 회전마다 **계산해서 배운다** | 세션 간 이어간다 |
| **판정주기** | 판정이 늦는 양 | **잰다.** 안 배운다 | 저장 안 함. 품질에만 |
| **잔여보정** | 설명 안 되는 나머지 | 최종 오차로 **배운다** | **모드별로 따로** |

**세 개를 나누는 이유가 있다.** 하나로 뭉쳐 "최종 오차가 0 이 되도록" 배우면
화면·기록 같은 **그때그때 사정까지 τ 가 흡수해서**, 조건이 바뀌면 안 맞는다.

```
τ      = (멈춘 뒤 각) − (정지명령 시점 각)  ÷  정지명령 시점 각속도
             ↑ 둘 다 정지명령 시점부터 잰다  →  판단이 언제 났든 무관.  순수한 물리
```

**좌/우 × 큰각/작은각으로 나눠서 배운다.** 한 값으로 뭉뚱그리면
한쪽은 항상 지나치고 한쪽은 항상 모자란다.

### 4-2-1. 정지 판정은 데이터가 도착하는 곳에서 한다 ★

메인 루프가 판정하면, 루프가 밀리는 만큼 늦게 멈춘다.

```
메인 루프(28~73 ms)가 판정  →  판정주기/2 = 14~37 ms  →  4.5도/s 면 0.06~0.16도
                               화면을 켜거나 기록이 밀리면 회전 정확도가 같이 나빠진다
```

**그래서 판정을 "그 데이터가 도착하는 곳" 으로 옮긴다.**

```
회전  →  자이로 샘플이 오는 곳 (200 Hz)   판정주기/2 = 2.5 ms  →  0.011도
직진  →  검출이 끝나는 곳   (30 Hz)      판정주기/2 =  16 ms  →  5 mm
계획  →  아무 데나. 느려도 된다
```

**메인 루프가 얼마나 느리든 정지는 제때 난다.** 화면·기록 걱정이 구조적으로 사라진다.

### 4-2-2. 스레드를 어떻게 나누나

**나누는 이유는 하나뿐이다: "이것이 저것을 기다리면 안 된다."**

| 쌍 | 기다리면 안 되나 | 판정 |
|---|---|---|
| 화면 ↔ 제어 | 화면이 느려도 제어는 가야 한다 | **나눈다** |
| 검출 ↔ 제어 | 검출이 끝나야 판정할 수 있다 — 기다리는 게 당연하다 | **안 나눈다** |
| 자이로 ↔ 제어 | 회전 중 5 ms마다 판정해야 한다 | **나눈다** |
| 기록 ↔ 전부 | 디스크가 멈칫해도 아무도 안 기다린다 | **나눈다** |

```
메인 스레드     화면 + 키                                   가벼운 일만
제어 스레드     검출 · 자세 · 계획 · 명령 · 학습 · [직진 정지 판정]   ★우리가 만든다
SDK 콜백       자이로 적분 · [회전 정지 판정]                (RealSense 가 준다)
기록 스레드     파일 쓰기                                    ★우리가 만든다
CANBusOwner    CAN 송신                                     (광운대 control.py 가 만든다)
```

**우리가 만드는 스레드는 둘뿐이고, asyncio 는 안 쓴다.**

**나누지 않은 것은 전부 제어 스레드 안에서 순서대로 돈다:**
```
프레임 받기 → 태그 검출 → 자세 계산 → [직진이면 정지 판정] → 계획 → 명령 → 학습 → 기록 쪽지
```
검출이 끝나야 자세가 나오고, 자세가 나와야 계획한다. **기다리는 게 당연한 순서라 나눠도 얻는 게 없다.**
자이로는 RealSense SDK 가 콜백으로 준다(광운대 `imu_stream.py` 의 `__call__(self, frame)`).
CAN 스레드는 광운대 `control.py` 가 직접 만든다(`threading.Thread(name="CANBusOwner")`).

**공유 상태가 네 군데뿐이다:**
```
제어 → 자이로 콜백 :  목표각 하나        (쓰기 1곳, 읽기 1곳)
자이로 콜백 → 제어 :  끝났다 + 결과
제어 → 화면       :  최신 패킷 한 칸     (큐가 아니라 덮어쓰기)
전부 → 기록       :  큐
```

#### 광운대 구조에서 가져온 것

`runtime_threads.py` 첫 줄이 전략 전부다:
> *Single control owner, latest-only presentation, bounded background file IO.
> No camera, inference model or FSM object is owned by the presentation thread.*

| 가져올 것 | 왜 |
|---|---|
| **제어를 메인 스레드에서 뺀다** | cv2 창은 메인에서만 안전하다. 제어가 화면에 안 묶인다 |
| **화면은 "최신 것만"** | `packet, self.latest = self.latest, None` — 밀린 프레임이 줄을 안 선다 |
| **화면은 시간으로 제한** | `next_display = now + 1.0/fps` |
| **화면 스레드는 중요 객체를 안 만진다** | 규율로 결합을 원천 차단 |
| **드롭은 명시적으로 센다** | 조용한 유실이 없다 |

그쪽은 **회전 정지도 송신 스레드가 한다**(`arm_timed_rotation` → 마감 시각을 CAN 스레드가 들고 있다).
같은 생각이다. **다만 그쪽은 시계를 들고 있고, 우리는 실제 회전각을 들고 있다.**

> **asyncio 를 안 쓰는 이유.** 스레드는 일꾼을 여러 명 두고 OS 가 번갈아 시키는 것이고,
> asyncio 는 **일꾼 한 명이 여러 일을 번갈아 하되 "기다릴 때 스스로 비켜주는"** 것이다
> (`await asyncio.sleep(0.010)` 이 비켜주는 지점).
> 락이 필요 없어 좋지만 **비켜주지 않는 일이 하나라도 있으면 전부 멈춘다.**
> 검출 21.8 ms 동안 CAN 송신이 멈추면 안 된다.
> 광운대도 같은 이유로 스레드로 갈아탔다 — 신버전 `control.py` 에는 `async`/`await` 가 0개다.
> (구버전 `control_forklift_v2.py` 는 asyncio 38곳. 우리는 신버전을 쓰므로 해당 없다 — 8절.)

#### 스레드라서 반드시 해야 할 안전 조치 넷

전부 해결 가능한 것들이다. 빠뜨리지 않게 적어둔다.

**① 스레드가 조용히 죽는다** ★ 제일 위험
```
자이로 콜백에서 예외 → 그 스레드만 죽는다. 프로그램은 계속 돈다
                     → 회전 정지 판정이 사라진다 → 차가 계속 돈다
```
단일 스레드면 예외가 나면 전부 멈추는데, **스레드는 일부만 죽고 나머지가 태연히 돈다.**
```python
def worker():
    try:     control()
    except BaseException as exc:  fail(exc)      # 어떤 예외든 잡아서
    finally: request_stop()                      # 전체 정지를 건다
```
(광운대 `runtime_threads.py` L320-332 의 방식 그대로.)
그리고 4-3 의 **`gyro_stale`** 이 감시 역할을 한다 — 샘플이 N ms 넘게 안 처리되면 제어가 알아채고 정지.

**② 레이스 — 목표가 판정 도중에 바뀐다**
```
나쁨:  target.angle = 5.0;  target.dir = "L"      두 줄 사이에 끼어들 수 있다
좋음:  self.target = Target(angle=5.0, dir="L")   한 번에 바뀐다. 중간 상태가 없다
```
**공유 객체를 절대 수정하지 않고, 새로 만들어 바꿔 단다.**

**③ Ctrl+C 가 전부를 안 멈춘다**
```
파이썬은 KeyboardInterrupt 를 메인 스레드에만 준다
   →  제어 스레드는 모르고 계속 명령을 낸다
```
공유 정지 Event 하나를 모든 루프가 매 바퀴 확인하고, `join(타임아웃)` + `daemon=True` 로 받친다.

**④ 재현이 안 된다** — 안전 문제는 아니지만 아프다. 같은 입력이어도 스레드 순서가 달라진다.
기록에 **스레드 이름·시각·상태 전이**를 남겨 나중에 되짚을 수 있게 한다.

**그리고 안전망 하나가 공짜다:**
```python
arm_timed_rotation(명령, 최대시간)      # 광운대 신버전에 이미 있다
   →  우리 코드가 다 죽어도 CAN 스레드가 최대시간에 차를 세운다
```

> **왜 단일 스레드로 안 가나.** 단일이면 검출 21.8 ms 동안 전부 멈춘다 —
> 회전 정지가 그만큼 늦으면 0.1도다(예산 0.5도의 1/5). CAN 송신도 같이 멈춘다.
> 회전 중에만 다른 일을 쉬는 절충안도 되긴 하지만(정확도 차이는 0.5 mm 로 무의미하다),
> **화면이 회전 2~3초 동안 멈추고, 나중에 회전 중에 뭔가 더 하려면 구조를 다시 짜야 한다.**
> 그래서 스레드로 간다. 대신 **새로 만드는 스레드를 둘로 줄여** 위험을 최소화한다.

#### 스레드로 빼도 GIL 경합은 남는다

```
파이썬은 스레드가 여러 개여도 파이썬 코드는 한 번에 하나만 돈다 (GIL)

검출(apriltag·OpenCV)  C 코드라 GIL 을 놓는다   →  진짜 병렬  ✓
화면(cv2)              대부분 C                →  거의 병렬  ✓
기록(JSON 직렬화)      순수 파이썬             →  GIL 을 쥔다 ✗
자이로 적분            순수 파이썬             →  GIL 을 쥔다 ✗
```

**즉 "판정주기 2.5 ms" 는 낙관적이다.** 실제로는 **2.5 ms + GIL 대기**다.
파이썬 기본 전환 간격이 5 ms 이므로 최악 `5 ms × 4.5도/s = 0.022도`.

```
① 자이로 콜백이 하는 일을 최소로   적분 한 번 + 비교 한 번. 직렬화는 큐 건너편에서
② sys.setswitchinterval(0.001)   최악 대기 5 ms → 1 ms
③ ★재서 확인한다                자이로 처리 간격 p99 를 품질(D)에 기록
                                  200 Hz 면 5 ms. p99 가 15 ms 면 GIL 대기가 있다는 신호
```

**광운대는 GIL 을 전혀 손대지 않았다**(`setswitchinterval`·`multiprocessing`·우선순위 전부 없음).
**필요 없었다는 뜻이지 괜찮다는 뜻이 아니다** — 그쪽 허용치는 20도다.
**먼저 재고, 필요하면 그때 간다.**

### 4-2-3. 광운대의 규칙과 맞대보면

```python
# 그쪽이 실제로 쓰는 것 (controllers.py)
should_stop = bool(live_stop or overshot or hold_reached)
def should_stop_now(...): return False      # live_stop 은 항상 False

# 즉:  경과시간 ≥ 출발지연 + 목표각 ÷ (각속도 × 학습배율)    또는   목표를 지나침
#                  ↑ 적합 상수            ↑ 관성이 이미 녹아 있다
```

| 우리 항 | 광운대 | |
|---|---|---|
| 남은각 (자이로 실시간) | **없음** — 시계를 본다 | 카메라가 2도 낡아서 실시간 판정을 못 한다 |
| ω (지금 각속도) | 적합된 각속도 × 학습배율 | 실제 속도가 아니라 모델이 예상하는 속도 |
| τ (관성, 따로) | **없음** — 각속도에 녹여둠 | 허용치 20도라 나눌 필요가 없었다 |
| 판정주기/2 | **없음** | 대신 송신 스레드가 판정해 루프 지연 자체를 없앴다 |
| 잔여보정 | **없음** | |
| — | **출발지연** (적합 상수) | 시계 기반이라 필수. 우리는 **안 쓴다** — 기다리면 되니까 |
| — | 지나침 backstop (카메라) | 우리는 β 교차확인이 그 역할 |

**그쪽은 "예상대로 될 것이다" 로 돌고, 우리는 "지금 어떤지 보고" 돈다.**

### 4-3. 멈추는 이유는 네 가지

| 이유 | 언제 | |
|---|---|---|
| 예측 도달 | 위 계산이 목표에 닿음 | 정상. 대부분 이걸로 |
| 넘어감 | 목표를 이미 지나침 | 안전망 |
| 시간 초과 | 너무 오래 돌고 있음 | 이상. 기록하고 멈춘다 |
| **자이로 끊김** | **마지막 샘플이 너무 오래됨** | **즉시 정지. 그 회전은 실패로 기록하고 태그로 재측정** |

마지막 항목이 없으면 **자이로가 죽은 채로 계속 돈다.** 회전 명령 자체에도 각도 상한을 걸어
자이로가 죽어도 도는 최대 각이 유한하게 한다.

### 4-4. 출발했는지 확인한다

명령을 보내고 **1.0~1.5초** 동안은 아무 일도 안 일어난다. 이때 "안 도네?" 하고 다시 명령하면
두 배로 돈다. **자이로가 "돌기 시작했다" 고 말할 때까지 기다린다.**

### 4-5. 한 번에 얼마나 도나 — 기하가 정한다

```
회전각 = 원하는 경로각 − 지금 방향
경로각 = atan( 지울 좌우 ÷ (지금 거리 − 태그컷) )        ← 도착점(태그컷, 법선 위)을 겨눈다
```
"갈 거리" 가 아니라 **도착점까지 남은 거리**로 잰다. 그래야 3-2 의 통로와 같은 삼각형이다.

| 상황 | 지울 좌우 | 도착점까지 | 경로각 |
|---|---|---|---|
| 멀리서 (8 m) | 2.0 m | 4.7 m | 23도 → **상한 17.1 에서 잘림** (두 걸음) |
| 중간 (5 m) | 0.5 m | 1.7 m | **16도** |
| 가까이 (4 m) | 0.1 m | 0.7 m | 8도 |
| 마지막 (3.5 m) | 0.03 m | 0.2 m | 8.5도 — 회전 자체가 좌우를 ~20 cm 움직여(4-6, 중심 1.5 m 가정) 말이 안 된다. 3 cm 는 그 전에 지우거나 비켜서기(3-9) |

**오차가 줄면 각도도 저절로 줄어든다.** 일부러 잘게 쪼개지 않는다 —
한 걸음이 약 12초라 1도씩 지우면 몇 분이 걸린다. 회전이 좌우도 움직이므로(4-6) 계획기는 회전중심을 넣어 센다.

#### 상한 — 17.1도 (광운대 실측 범위의 끝)

광운대 회전 모델은 `각도 = 13.6676 × 유지시간 − 17.0398`(motion_trajectory.selected.json, 강도 30) 이고
**유지시간은 2.5 s 까지만 쟀다**(rotation_endpoint.selected.json "Hold cap remains 2.5s"):
```
TURN_HARD_MAX_DEG = 13.6676 × 2.5 − 17.0398 = 17.1도
```
물려받은 씨앗(각속도·출발지연·τ)이 이 각까지만 실측이라 우리도 여기까지만 쓴다. 화각으로는 더 돌 수 있다
(반화각 35도. 광운대는 55도 화각에서 20도) — 우리 실측이 쌓이면 올린다. **회전 중심이 확정되기 전에는 5도**(4-6).
사이드스텝의 ±90도는 예외다(3-2) — 그 뒤 반드시 다시 재기 때문이다.

#### 하한 — 정지지연 동안 도는 각 (`learner.rot_floor_deg`)

움직이기 시작한 걸 알아채자마자 끊어도 정지 명령이 먹기까지(광운대 실측 0.352 s) 가속하며 돈다:
```
씨앗  rot_floor = ½ × 13.06도/s² × 0.352² = 0.81도       ← 유도값 (그쪽 ROT_RESPONSE_ACCEL · STOP_DELAY). 실측 아님
실측  calibrate rotfloor: "움직이자마자 정지" × 양방향 5회 → 최대각 → config ROT_FLOOR_DEG     ← 이게 씨앗을 덮는다
```
하한 아래 요청은 **거부하고 학습에서도 뺀다** — 지나치는 게 정상이라 잔여를 오염시킨다. 그때는 회전 대신 비켜서기(3-9).

**광운대의 2.5도(`ROT_MIN_COMMANDABLE_ANGLE_DEG`)는 우리 하한이 아니다.** 그쪽은 시계로 끊어서 짧은 명령을
못 맞추는 것이고, 우리는 자이로를 보고 끊는다. 미세 모드 0.5도도 그쪽 `# provisional` 이다.

### 4-6. 회전은 좌우 위치도 움직인다 ★중요

**"제자리 회전" 이 실제로는 제자리가 아니다.**

```
        회전 중심
           ●
      d ───┤
          📷 카메라

10도 돌면  →  카메라가  d × sin(10도)  만큼 옆으로 간다
```

**이 지게차는 궤도 차량이다.** 좌우 궤도를 반대로 돌려 제자리 회전하고,
그때 궤도가 땅에 대해 옆으로 미끄러진다. **회전중심은 그 미끄러짐의 저항이 균형을 이루는 점**이라
기하가 아니라 **마찰이 정한다.** 마스트·포크가 앞에 무거우므로 **앞쪽으로 치우친다.**

```
           회전중심 (앞바퀴 축)
              ●
   📷 ────────┤▐         뒷부분
   카메라     앞바퀴
      1.52 m       ← 카메라→접힌 포크끝 실측. 접힌 포크끝 ≈ 앞바퀴
```

**→ 회전중심은 카메라 앞 약 1.5 m 로 추정된다.**

| 출처 | 값 | 판정 |
|---|---|---|
| 앞바퀴 기하 (위) | 카메라 **앞** 1.5 m | 가장 유력 |
| 9/7 방위각 비율 0.77~0.95 (n=13) | 카메라 **앞** 0.4~1.2 m | 같은 방향 |
| 광운대 실측 | 그쪽 카메라 **뒤** 0.68 m | 카메라 위치가 다름 |
| **v2 config** | 카메라 **뒤** 1.46 m | **폐기** — 크기는 같고 부호만 반대. 출처도 "8m·자이로 사망 1회 펄스" |

**부호를 틀리면 돌 때마다 반대로 보정한다:**
```
10도 회전 시 카메라 좌우 이동
   v2 예측 :  한쪽으로 25 cm
   실제    :  반대쪽으로 26 cm      →  51 cm 오차, 방향까지 반대
```
**9/7 의 좌우 왕복 실패에 이게 기여했을 가능성이 크다.**

**그래서 확정 전까지는 한 걸음 회전을 5도로 제한한다.**
(5도면 후보 둘의 차이가 1.07 × sin5도 = 9 cm 로 감당 가능하다.)

### 4-7. 회전 중심을 어떻게 재나 — 동심원 맞추기

**원리:** 제자리 회전하는 동안 카메라 위치는 회전 중심을 축으로 원을 그린다.
중심을 맞게 잡으면 반지름이 일정하다.

```
              ● 찾는 점
           ╱  │  ╲
         📷   │   📷      ← 회전하며 지나간 자리들
           ╲  │  ╱
             📷
```

**절차:**
```
① 3.5 m 에서 태그를 화면 정중앙에 맞춘다
② 5도 돌고 → 멈추고 → 조용해지면 → 자세 기록        (정지 상태에서만)
③ 처음 3 스텝으로 "태그가 화면에서 몇 배로 움직이나" 를 본다
      배율 < 1  →  중심이 앞.  ±40도까지 안전
      배율 > 1  →  중심이 뒤.  ±20도로 제한
④ 그 범위를 스윙한다 (가운데 통과). 25점 내외, 약 2분
```

**계산 두 가지를 같이 돌려 교차 검증한다:**

```
· 위치 + 방향 (주)    "5도 돌았는데 13.1 cm 움직였다 → 반지름 1.50 m"
                      스텝마다 독립적으로 나온다. 평균내면 ±1.2 cm
· 위치만     (검산)   광운대 `icr_fit.py` 방식(동심원 적합). ±3.1 cm
```

시뮬레이션(위치잡음 4 mm, 방향잡음 0.06도, 500회 — ★9/21 실측은 프레임 sd 39 mm · 0.59도로 10배 크다. 정지 창 평균으로도 31 mm.
최소제곱 오차는 작은 잡음에서 잡음에 비례하니 60도 스윙이 0.12 m 급이 돼 필요 정확도 ±0.07 m 를 못 지킨다 → 점을 더 찍거나 σ 실측 후 다시 돌린다):

| 스윙 | 위치만 (90% 오차) | 위치+방향 (90% 오차) |
|---|---|---|
| 20도 | 0.393 m ✗ | **0.030 m** ✓ |
| 40도 | 0.079 m △ | 0.015 m ✓ |
| **60도** | **0.031 m** ✓ | **0.012 m** ✓ |

필요 정확도는 **±0.07 m**(25도 회전에서 좌우 30 mm 예산). **5배 여유.**

**명령한 각도는 계산에 안 들어간다.** 관성 때문에 스텝이 제각각이어도 무관하다:

| 관성 산포 | 90% 오차 | 실제 스텝 |
|---|---|---|
| ±0.5도 | **1.25 cm** | 3.9 ~ 6.1도 |
| ±2.0도 (극단) | 1.52 cm | 1.0 ~ 9.0도 |

**자이로는 "5도만 돌아라" 실행에만 쓰고 계산에는 안 들어간다.**
→ 9/7 의 "회전팔이 틀렸나 자이로 배율이 틀렸나" 애매함이 원천적으로 없다.

**덤:** 회전중심의 **좌우 오프셋**도 같이 나온다(광운대는 미측정으로 비워둔 값).

#### 한 번의 측정으로 "고정인가" 까지 답한다 — RMS

25개 점으로 중심을 맞추면 **얼마나 잘 맞는지**가 같이 나온다. 따로 실험하지 않는다.

```
중심까지 거리:  1.502  1.498  1.511  1.495  1.504  …   (전부 같아야 한다)
어긋남      :    0     −4     +9     −7     +2    mm
RMS         :  약 5.6 mm   = "평균 이만큼 원에서 벗어난다"
```

**기준선은 정지 창 평균의 σ(밀림, 3-6 — run 이 출발 뒤 잰다)다.** 아래 5·15 mm 는 ±4 mm 시절 값(잡음의 약 1배·3배)이라
★σ 실측 후 같은 배수로 다시 정한다.

| RMS | 뜻 | 조치 |
|---|---|---|
| **5 mm 이하** | 잡음만큼만 어긋난다 | **중심이 고정이다. 그 값을 쓴다** |
| 5~15 mm | 조금 흔들린다 | 쓰되 주행 중 갱신을 켠다 |
| **15 mm 이상** | 원이 아니다 | 좌·우 따로 맞춰본다 → 그래도 크면 한 번 더 측정 → 또 크면 회전 상한을 줄이고 갱신 |

좌·우를 따로 맞춰 각각 작아지면 **좌우 중심을 따로 쓴다**(광운대 `icr_fit.py` 의 `mirror` 검사).

> **궤도라서 변하나?** 광운대가 같은 장비에서 **한 번 재서 박아두고** 주행 중 갱신 없이 쓴다
> (`CAMERA_TO_ROT_CENTER_Z_M = -0.68  # measured`). 안정적이라는 증거다.
> 다만 그쪽 허용치가 40배 느슨하다. **추측하지 말고 RMS 로 답한다.**

**검증 기준:**
```
결과  −0.4 ~ −1.8 m (카메라 앞)  →  ✅ 9/7 로그·사진 비례와 맞다. 그 값을 쓴다
      양수 (카메라 뒤)           →  ⚠️ 예상과 반대. 측정을 다시 본다
      RMS 15 mm 이상            →  위 표대로
```

### 4-8. 회전 정확도 — 지금 아는 것

**9/7 실주행 56회**(리드 켠 실제 컨트롤러):
```
절대오차 중앙값 0.61도,  표준편차 1.10도
0.5도 이내 43% / 1.0도 이내 57% / 2.0도 이내 96%
요청각 중앙값 88.6도 (사이드스텝 90도가 대부분).  3도 미만 요청은 1회뿐
```

**9/21 의 "잔차 ±1.5도" 는 컨트롤러 성능이 아니다.** 코드에 이렇게 적혀 있다:
```python
async def rotate_closed(self, deg, why="", lead_deg=0.0):
    """**리드 0** — 오버슈트를 그대로 재려는 것이다."""
```
**일부러 관성 보정을 끄고 관성 자체를 잰 값**이다.

**블라인드 1.78 m 에 넣으면:**
```
중앙값 0.61도  →  19 mm   ✅ 예산 안
1σ    1.10도  →  34 mm   ⚠️ 살짝 초과
```
빠듯하다. 지금 리드가 **2.5도 고정값**인데, **예측 정지**(남은각 ≤ 각속도 × 관성시간)로
바꾸면 여기서 좋아진다.

### 4-9. 최소 회전 — 하한 하나, 강도 하나

최소 회전각은 4-5 의 **하한(rot_floor)** 이다. 씨앗 0.81도(유도), config ROT_FLOOR_DEG(calibrate 실측)가 덮는다.

**왜 0.5도 언저리가 중요한가.** 방향은 "재고 → 고치고 → 다시 재고" 로 맞춘다:
```
① 재보니 +2.3도  →  −2.3도 돌려라  →  실제 −1.7도  →  남은 +0.6도
② 재보니 +0.6도  →  −0.6도 돌려라  →  하한이 2도면 여기서 막힌다
```
얼마나 틀어졌는지는 σ(3-6)만큼 안다. 고칠 수가 없을 뿐이다.
하한보다 작은 오차는 **돌지 않고 좌우로 비켜서서**(3-9) 상쇄한다 — 1.78 m 블라인드에서 0.8도는 25 mm 다.

**두 번째(약한) 강도는 만들지 않는다.** 이유 셋:
```
· 각속도·출발지연·τ·하한이 전부 강도를 탄다 → 강도마다 씨앗 한 벌이 필요한데, 있는 건 광운대 30 한 벌뿐
· 우리 9/7·9/21 회전 측정은 강도 20 이라 씨앗으로 못 쓴다 (8-0)
· 하한은 "약하게 돌아서" 가 아니라 "일찍 끊어서" 낮춘다 — 자이로가 출발을 5 ms 만에 알려준다 (4-4)
```
강도 바꾸기·데드밴드 찾기(옛 4-9 의 10/15/20 표)는 **실차 한 판 뒤 하한 실측이 예산을 못 맞출 때만** 다시 꺼낸다.

#### 하한 재는 법 (calibrate rotfloor)
```
정지 상태, 태그를 보며, 강도 30
   "자이로가 움직였다고 하면 즉시 끊어라" 를 좌 5회 · 우 5회
재는 것  ① 총 몇 도 돌았나 → **최대각**이 rot_floor       ② 5번이 얼마나 일관적인가 (흩어짐도 기록)
```
평균이 아니라 최대를 쓴다 — 하한 아래로 요청했다가 지나치는 쪽이 비싸다.

### 4-10. 회전 한 번에서 무엇을 배우나

**네 시각과 자이로 각도만 있으면 전부 나온다.**

```
 t1  명령 보냄
  │  ← 출발 지연
 t2  자이로가 "움직였다"
  │  ← 실제로 도는 구간
 t3  정지 명령 보냄
  │  ← 관성
 t4  자이로가 "멈췄다"
```

| 얻는 값 | 계산 | 쓰는 곳 |
|---|---|---|
| 출발 지연 | `t2 − t1` | **제어엔 안 쓴다.** 건강 검사·시간 예산 |
| 각속도 | `(ψ(t3) − ψ(t2)) ÷ (t3 − t2)` | 예측 정지 |
| **관성 시간 τ** | `(ψ(t4) − ψ(t3)) ÷ ω(t3)` | **예측 정지. 배운다** |
| 최종 오차 | `ψ(t4) − (영점 + 목표각)` | **잔여보정. 배운다** |

**τ 와 최종 오차를 다른 곳에 넣는 게 핵심이다**(4-2).
τ 는 모드를 안 타고, 잔여보정만 모드를 탄다.

```
τ     ← EMA(τ, 관측)        [좌/우 × 큰각/작은각]
잔여  ← EMA(잔여, 최종오차)  [좌/우 × 큰각/작은각 × 모드]
```

**회전할 때마다 짝 하나씩 공짜로 쌓인다.** 따로 측정 단계를 만들 필요가 없다.

#### 첫날 — 아무것도 안 배운 상태

```
τ      →  모른다. 보수적으로 크게 잡는다 (일찍 멈춘다)
잔여   →  0
```
**일찍 멈추는 건 싸고(한 번 더 돌면 됨), 지나치는 건 비싸다.** 모르면 크게 잡는다.

#### 직진도 같은 틀 — 그리고 측정 나이가 공짜로 흡수된다

```
남은거리 ≤ v × ( 측정나이 + τ_직진 + 판정주기÷2 ) + 잔여보정
```

카메라는 "조금 전" 을 알려주므로 **낡은 만큼도 같이 빼줘야 한다.** 그런데:

```
정지명령 낼 때 읽은 거리  d_읽음   ← 움직이는 중이라 낡았다
완전히 선 뒤 읽은 거리    d_최종   ← 안 움직이니 낡음 없음

(d_읽음 − d_최종) ÷ v  =  나이 + τ        ← 필요한 합이 그대로 나온다
```

**①(노출→도착)을 몰라도 된다.** 평소처럼 빼서 나누면 이미 들어 있다.
다만 ②(검출 시간)는 CPU 부하로 변하므로 **빼고 배운다:**
```
배울 값  τ_학습 = (d_읽음 − d_최종) ÷ v − ②(그때 실측)      = ① + 진짜 관성. 상수
쓸 때    d_읽음 ≤ 목표 + v × ( ②(지금 실측) + τ_학습 + 판정주기÷2 )
```
**변하는 건 매번 재고, 안 변하는 건 배운다.**

#### 시계가 셋이다 — `src/utils/clock.py` (2026-09-30 결정 10)

9/21 로그에서 확인한 것:
```
카메라 프레임 스탬프   1789968377.5    1970년 기준(epoch). global_time 을 켜면 이렇다
CAN 송신 시각          monotonic_ns    광운대 control.py
우리 계산              2847.3          time.monotonic. 부팅 기준
```
그냥 빼면 "사진이 얼마나 낡았나" 가 **−17억 초**가 된다 — 미리 끊는 계산이 무의미해지고 태그를 놓쳤을 때 안전망이 영영 안 걸린다.

**규칙:** 내부 시각은 전부 `clock.now()`(monotonic). 카메라 스탬프는 `CameraClock.see(ts, t_arrival)` 로 우리 시계로 바꿔서만 쓴다.
`driver.set` 의 시각도 `clock.now()`. 기록에만 `clock.wall_from(t)` 로 벽시계를 병기한다.

**기준점 잡는 법:** 스탬프가 epoch 라고 가정하지 않는다. `도착시각 − 스탬프` 를 처음 30 프레임(WARMUP) 동안 보고
**최소값**을 기준점으로 잡는다 — 제일 빨리 온 프레임이 진짜 바닥에 제일 가깝다. 그 뒤 더 빠른 프레임이 오면 그쪽으로만 당긴다
(한 방향. 당기면 "더 낡았다" 쪽이라 안전하다). 바닥 지연만큼은 상수라 τ 에 흡수된다(위).
`age_ok`: −1 ms ≤ 나이 ≤ 0.30 s(광운대 MAX_MEASUREMENT_AGE_SEC). 음수면 시계가 섞인 것 → `why="clock"`(3-6).
출발 전 `clock.check()` 가 기준점이 잡혔는지 본다(12-0).

## 5. 삐뚤게 달린 것을 어떻게 다루나

카메라와 태그는 실험마다 붙였다 뗀다. **완벽히 똑바로 다는 건 불가능하다.**
그런데 1도만 틀어져도 예산(3 cm)을 먹는다.

### 5-1. 삐뚤어짐은 세 종류다

```
① 액자처럼 기울어짐         ② 좌우로 비스듬히 붙음        ③ 카메라가 틀어져 달림
   (태그면은 벽에 딱 붙음)     (태그가 옆을 봄)              (광축이 차체 정면과 어긋남)
```

| | 1도일 때 좌우 오차 | 왜 |
|---|---|---|
| ② 태그 좌우 | **35 mm** | 지도 전체가 돌아간다 |
| ① 액자 기울기 | 17 mm | 카메라가 태그보다 1.10 m 아래라 높이차가 좌우로 샌다 |
| ③ 카메라 | 31 mm | 눈 감고 가는 1.78 m 구간에서 |

### 5-2. ② 는 벽에 평평하게 붙여서 없앤다

**태그면 = 벽면**이 되므로 태그가 보는 방향이 벽이 보는 방향과 같아진다.

```
· 딱딱한 평판(포맥스·알루미늄 복합판)에 인쇄물을 붙인다
· 그 판을 벽에 밀착시킨다.  받침대·거치대 금지
· 종이 말림·테이프 기포 금지 (휘면 계산이 직접 틀어진다)
```

### 5-3. ① 은 중력으로 자동 측정한다

```
가속도계  →  카메라에서 본 "아래" 방향  (중력. 절대 기준)
태그 계산 →  태그의 가로축 방향

태그가 똑바르면 둘이 직각.  기울어져 있으면 그 각도가 바로 나온다
```

- 중력은 절대 기준이라 **태그와 카메라 기울기를 한꺼번에** 잡는다
- **정지 중에만 유효**하다(움직이면 가속도가 섞임). 우리는 어차피 멈춰서 보므로 문제없다
- 정밀도 **0.1도 이내**

run 이 출발 뒤 정지 60초 창의 중앙값으로 넣고(`Estimator.set_tag_roll`, 2026-10-02), 주행 중에는 멈출 때마다 다시 재서
**달라졌으면 경고**한다. 거리에 따라 값이 변하면 태그가 휜 것이니 그것도 잡힌다.

⚠️ **가속도계가 살아 있어야 한다.** 9/21 에 자이로 열기에서 겪은 문제와 같은 스트림이라,
`calibrate.py device` 가 **가속도계부터 확인**한다. run 도 출발 뒤 기준선 창에서 같은 값을 쓴다.

### 5-4. ③ 은 똑바로 가보면 알 수 있다

```
태그를 보며 3 m 직진  →  좌우가 얼마나 변했나  ÷  간 거리  =  틀어진 각
```

**문제:** 기계 결함이나 노면 때문에 그냥 직진만 해도 차가 휠 수 있다.
**해결: 자이로가 휜 것을 본다.**
```
진짜 똑바로 갔다면   →  자이로 각도 변화 ≈ 0
휘어갔다면          →  자이로가 알려준다  →  그 시행은 버린다
```

**3.5 m 에서** 시작·끝을 정지 창 평균(9/21 30프레임 평균 sd 31 mm)으로 재면 한 번에 atan(√2 × 31 mm ÷ 3 m) ≈ 0.8도 급이다.
(2026-10-02: 실행이 veer 를 안 쓰므로 측정 단계는 없앴다 — 필요하면 run 기록의 직진 다리에서 사후 계산.) ★σ 실측 후 정밀도 확정.

### 5-5. 그래도 남는 것 — 벽이 진입축에 직각이 아닐 수 있다

평평하게 붙이는 건 **태그와 벽의 관계**를 잡아줄 뿐이다.
**벽 자체가 탑재부 진입 방향에 직각이 아니면** 태그도 같이 틀어져 있다.
**태그만 봐서는 절대 못 알아낸다** — 태그가 기준이니까.

### 5-6. 정답 자세 — ②⑤ 와 태그 위치까지 한꺼번에 푼다

**질문을 바꾼다.**
```
옛날:  "나는 세상 기준으로 어디에 있나?"     ← 태그가 틀어지면 틀림
새것:  "지금 보이는 게 그때랑 같나?"        ← 틀어짐이 양쪽에 똑같이 들어가 상쇄
```

**절차 (`calibrate.py camyaw` 가 안내·기록):**
```
1. 지게차를 탑재부에 손으로 정확히 넣는다 (양옆 틈이 같도록)
2. 자이로 영점을 잡고, 태그가 보일 때까지 후진해서 나온다
3. 그 지점에서 기록:  카메라가 말하는 좌우·방향,  자이로가 말하는 돈 각도
4. 자이로가 0.3도 넘게 돌았으면 버린다 (똑바로 안 나온 것)
5. 3~5회 반복 평균  →  이것이 "정답 자세"
```

**검증 루프 (이게 진짜 마무리):**
```
정답 자세 재현 → 눈 감고 진입 → 실제로 얼마나 치우쳤나 재기
   4 cm 우측으로 들어감  →  정답 자세를 4 cm 보정  →  재시도.  2~3회면 수렴
```

**상쇄되는 것:** 벽 틀어짐, 카메라 틀어짐, 태그의 좌우 위치, 렌즈 보정 오차.

### 5-7. 그래도 각각 따로 재는 이유

- 정답 자세가 잡아야 할 양이 줄어 **검증 루프가 빨리 수렴한다**
- 값이 **이상하면 그때 알 수 있다**(태그가 휘었다, 카메라가 헐거워졌다)
- **주행실험에는 탑재부가 없어서 정답 자세를 못 잡는다.** 그때는 5-3·5-4 만으로 간다

## 6. 주행하며 배운다 — 적응형 4종

지연과 관성이 매번 다르니, **미리 정한 숫자로는 못 맞춘다.** 대신 돌면서 배운다.

| 무엇을 배우나 | 어떻게 |
|---|---|
| **회전 속도** (좌/우 따로) | "명령 1초에 실제 몇 도" 를 매 회전 후 갱신 |
| **회전 오버슈트** | 30도 시켰는데 40도 돌았으면 다음엔 명령을 30/40 으로 줄인다 |
| **직진 속도** | 전진 중 (시각, 거리) 의 기울기. 한 걸음에서 프레임 수십 개가 나온다 |
| **경로** | 몇 걸음 앞을 그려보고 첫 걸음만 (3-2) |

**갱신은 조금씩 한다:** `새 값 = 옛 값 + 0.50 × (관찰 − 옛 값)`(광운대 ROT_ADAPTIVE_SLOPE_ALPHA), 0.5~2.0 배로 묶는다.
(광운대 `adaptive_slope.py` L24-36 과 같은 식)

**오버슈트는 줄이기만 하고 늘리지 않는다.** 넘어가는 게 모자라는 것보다 비싸기 때문이다
(광운대 `controllers.py` L21-37 의 철학).

### 6-1. 각도 구간을 나눌지는 데이터를 보고 정한다

9/21 관측은 **느리게 돌 때 관성 시간이 더 길다**고 말한다(느릴 때 0.5초 / 빠를 때 0.33초).
**그런데 느린 쪽 표본이 4개뿐이라 이걸로 구간을 나누는 건 성급하다.**

**광운대는 각도로 안 나눈다.** 학습 키가 `ROT_LEFT`/`ROT_RIGHT` 뿐이고
(`top.py` `_session_slope.observe(self._rotation.command, ...)`),
모든 각도가 같은 학습기에 들어간다. 대신 **"최소 회전각" 만 모드에 따라 다르다**
(평소 2.5도 / 마지막 정렬 0.5도).

```
1단계 (시작)      τ 하나.  좌/우만 구분한다.  각속도는 기록만 한다
2단계 (첫 실차 후)  τ 가 각속도에 따라 변하는 게 보이면  →  그때 관계식으로 올린다
                                                       안 변하면 그대로 둔다
```

**복잡도를 미리 사지 않는다.** 기록(G 원시 짝)에 `omega_at_stop` 과 `tau_observed` 가
짝으로 남으니 **첫 실차 한 판이면 답이 나온다.**

### 6-2. 관성은 각속도에 녹이지 말고 따로 뺀다

광운대는 관성을 **총 회전각에 포함시켜** 통째로 맞춘다(`uses_embedded_inertia = True`).
허용치가 20도라 나눌 필요가 없어서다. **우리는 0.5도라 뭉뚱그리면 안 된다.**

### 6-3. 배운 값을 쌓는다 — 무엇을 어떻게 기록하나

```
EMA 계수 0.50  →  수렴까지 2~4 표본
한 번의 도킹    =  걸음 6~12번       →  첫 도킹에서는 수렴할 때쯤 끝난다
```
광운대는 프로그램을 끄면 배운 게 사라진다(세션 단위). **우리는 쌓는다.**

#### 왜 쌓나 — 다섯 질문에 답하려고

```
① 오늘 값이 이상한가?                   →  이력과 비교
② 어느 값이 변하고 어느 값이 안 변하나?   →  세션을 가로질러 본다
③ 실패했는데 왜?                        →  조건·품질·학습·결과가 한자리에
④ 이 세션 값을 다음에 써도 되나?          →  조건이 같은지 판단
⑤ 나중에 새 질문이 생기면?               →  요약 말고 원시 짝이 남아야
```

**②가 제일 큰 수확이다.** 지금은 모든 값을 "매번 재야 하는 값" 으로 취급하고 있는데,
세션이 5~10번 쌓이면 갈린다:
```
회전 중심      안 변해야 정상  →  config 에 한 번 적은 값이 세션을 가로질러 맞는지 (calibrate 는 카메라 재장착 때만)
카메라 틀어진 각 변해야 정상    →  얼마나? ±0.2도면 무시, ±2도면 매번 필수
관성           변한다          →  얼마나? ±10%면 학습으로 충분
```

#### 다음 세션 초기값을 정하는 규칙
```
1. 품질 통과한 세션만 본다                (quality.passed)
2. 조건이 같은 것만 본다                  (B 의 무효화 표)
3. 최근 것부터 N 개                       (오래된 건 신뢰도를 낮춘다)
4. 중앙값을 쓰고, 흩어짐도 같이 넘긴다      (흩어짐이 크면 학습을 빨리 돌린다)
5. 없으면 → 조용히 기본값을 쓰지 않고 시끄럽게 경고
```
그리고 **첫 3걸음은 학습 계수를 크게(0.5)** 해서 오늘 조건에 빨리 붙게 한다.

값 하나를 세션 순서대로 한 줄에 뿌린다
   cam_to_rot_center_m  −1.47  −1.44  −1.51  −1.46   → 거의 안 변한다 ✓
   cam_yaw_offset_deg    0.42   1.13  −0.31   0.88   → 매번 다르다 (재장착)
   rot_coast_tau_L       0.31   0.29   0.44   0.30   → 세 번째가 튄다. 그날 뭐였지?

결과와 나란히 본다 — 실패한 세션들의 공통점이 있나
"τ 가 모드와 상관있나" 도 자동으로 본다 (전용 실험 없이)
```

### 6-4. 학습이 못 하는 것

```
물리적 하한(아무리 배워도 못 내려가는 최소 회전각)
측정 잡음
첫 몇 걸음 (배울 표본이 없다)
```
**학습은 측정을 대체하지 못한다.** 재둔 값을 그날 컨디션에 맞게 다듬을 뿐이다.

### 6-5. 관성은 하나로 정하지 않는다 (직진·회전 둘 다)

```
관성 = 속도 × 반응지연 + 속도² ÷ (2 × 감속도)
             ↑ 매번 다름      ↑ 하중·노면·온도·좌우로 변함
```

**반응 지연이 들어 있다 — 출발 지연(문제 2)과 같은 문제다.** 하나의 숫자로 못 박는다.

**광운대도 안 쟀다.** 코드에 그대로 적혀 있다:
```python
"""Selected delayed-linear ON-command regressions; coast is not fitted."""
note = 'ON-command trajectory; coast unmodeled; settle and remeasure'
def stop_now_margin_deg(...): return 0.  # Unknown coast; do not invent a live predictive coast margin.
```
**모르는 값을 지어내지 않는다는 규율이다. 우리도 따른다.**

**그리고 좌우에는 거의 영향이 없다:**
```
관성은 "진행 방향" 으로 더 가는 것
좌우로 새는 양 = 0.13 m × sin(0.5도) = 1.1 mm      ← 무시 가능
앞뒤 허용치 = 10 cm                                ← 느슨
```

**정말 중요한 곳은 두 군데뿐이다:**
```
① 태그 컷 3.3 m 을 지나쳐 버리면  →  정렬을 못 끝낸 채 눈이 먼다
② 탑재부 안쪽 벽                  →  충돌
```
**나머지 걸음은 지나쳐도 그 자리에서 다시 계획하면 그만이다.**

**그래서 비대칭으로 간다:**
```
지나치는 것 = 비싸다,  못 미치는 것 = 싸다
   →  보수적으로(일찍) 멈추고, 모자라면 한 번 더 간다
   →  지나치면 안 되는 두 곳에만 여유를 크게
```

### 6-6. 기록이 주행을 망치지 않게

필드가 80개 가까이 된다. **기록이 주행을 죽이는 게 제일 현실적인 위험이다.**

**① 기록에서 난 예외는 밖으로 안 나간다**
```python
try:    logger.rotation(...)
except Exception:  self.log_errors += 1      # 세고 넘어간다. 주행은 계속
```
조용히 넘기지는 않는다 — `log_errors` 를 품질(D)에 넣고, 0 이 아니면 그 세션을 초기값에서 뺀다.
```
기록이 실패해서 주행이 멈추는 것   →  절대 안 됨
기록이 실패한 걸 모르는 것        →  그것도 안 됨
```

**② 판단 루프에서는 디스크를 만지지 않는다**
```
판단 루프  →  메모리 큐에 넣기만 (약 1 µs)
별도 스레드 →  큐를 비워 디스크에 쓴다
큐가 차면  →  오래된 프레임 줄부터 버리고 센다 (dropped_rows)
              이벤트(회전·직진·결정)는 절대 안 버린다
              어떤 경우에도 판단 루프가 기다리지 않는다
```
직렬화 비용도 스레드로 넘긴다. 젯슨 SD카드가 수십 ms 멈칫해도 루프는 안 멈춘다.

**③ 줄 단위로 append. 한 장짜리 JSON 은 맨 마지막에만**
```
주행 중  →  frames.jsonl · events.jsonl 에 한 줄씩
주행 끝  →  그 줄들을 읽어 history/<세션>.json 한 장을 만든다
```
중간에 죽어도 그때까지가 다 읽힌다. 요약 만들기가 실패해도 **원시 줄이 남아 다시 만들 수 있다.**

**④ 먼저 멈추고, 그다음 기록한다**
```python
def stop(why):
    send_stop_frame()                 # ① 무조건 먼저. 기록 코드를 안 거친다
    try:  log_stop(why, ...); flush() # ② 그다음. 곧 죽을 수 있으니 바로 디스크로
    except Exception: pass
```
**순서가 전부다.** 멈추는 건 기록에 의존하지 않고, 기록은 멈춘 뒤에 한다.
**정지 기록만은 큐를 안 거친다** — 큐에 넣어두면 스레드가 비우기 전에 죽어서 사라진다.

`why` 는 정해진 목록에서만 (자유 문자열이면 나중에 셀 수 없다):
```
normal · emergency · ctrl_c · deadman · fork_guard · gyro_stale · tag_lost · timeout · exception
```

**프로세스가 통째로 죽는 경우:**
```
Ctrl+C · 예외   →  최상위에서 잡는다 → 멈추고 → 기록.  남는다 ✓
강제 종료·정전  →  못 한다
   ① 1초마다 flush        →  죽어도 마지막 1초치만 잃는다
   ② 다음에 켤 때 "닫힘 기록 없는 세션" 을 찾아 ended_unexpectedly 로 표시
      →  품질 검사에서 자동 탈락
```
**"왜 끝났는지 모르는 세션" 이 조용히 이력에 섞이는 걸 막는다.**

**⑤ 출발 전에 쓸 수 있는지 먼저 본다** — 폴더·권한·여유공간. 한 줄 써보고 지운다.
안 되면 **출발 거부.** 주행 중에 실패하는 것보다 낫다.

**⑥ None · NaN · inf 를 안전하게** — 학습 초기값은 대부분 None 이고, NaN/inf 는 JSON 규격에 없다.
쓰기 직전에 걸러 null 로. 숫자 자리에 문자열이 오면 **그 필드만** 버리고 센다(줄 전체를 버리지 않는다).

**⑦ dry-run 에서 기록 경로를 통째로 한 번 돌린다** — CAN 은 안 보내되 기록은 실주행과 똑같이.
80개 필드가 다 채워지고 요약까지 만들어지는지 노트북에서 걸러낸다.

**⑧ 기록 자체를 검사하는 테스트** — `tools/check/check_log.py`
```
가짜 주행 한 판 → 필수 필드 · 요약 생성 · history 반영 · index 갱신
일부러 None · NaN · 문자열을 섞어도 안 죽나
```

**⑨ 기록량에 상한** — 프레임 30 Hz × 3분 = 5,400줄(괜찮다), 자이로 200 Hz × 3분 = 36,000줄
(→ 회전 구간만 원시로, 나머지는 요약). 세션 폴더 크기 상한을 두고 넘으면 프레임부터 솎는다.

> **한 줄로:** 주행 > 기록. 기록 때문에 차가 멈추거나 늦어지는 일은 없다.
> 다만 기록이 실패한 사실은 반드시 남긴다.

#### 명령이 늦어지나 — 계산

```
CAN 보내는 것  →  별도 송신 루프(10 ms)라 우리와 무관.  실측 0.168 ms.  안 늦는다
판단이 늦는 것 →  루프가 막히면 그만큼 늦게 멈춘다
```

| 100 ms 늦으면 | | 허용치 | |
|---|---|---|---|
| 직진 (0.3 m/s) | 3 cm | 앞뒤 10 cm | 괜찮다 |
| **회전** (4.5도/s) | **0.45도** | **0.5도** | **✗** |

**→ 그래서 회전 판정을 자이로 스레드로 뺀다**(4-2-1). 그러면 루프가 밀려도 회전은 제때 멈춘다.
**화면·기록을 켜도 회전 정확도가 안 변한다.**

그리고 루프에서 제일 오래 걸리는 건 기록이 아니라 **검출**이다(중앙값 21.8 ms, p99 73.4 ms).
다만 9/21 의 루프 실측은 `n=3` 이라 **실제 루프 주기를 우리는 모른다** —
단계별로 재서 품질(D)에 남긴다.

## 7. 왜 이게 되는가

| 문제 | 어떻게 피하나 |
|---|---|
| 지연이 매번 다름 | **시계를 안 본다.** 남은 거리·남은 각을 보고 멈춘다 |
| 오차가 쌓임 | **한 걸음마다 다시 잰다.** 실제 도착한 자리에서 새로 계산 |
| 멀리서 값이 흔들림 | **못 믿으면 안 움직인다.** 각도 대신 화면 위치를 쓴다 |
| 정면에서 뒤집혀 보임 | 두 해의 재투영오차 비로 걸러낸다. 멀리선 각도를 안 쓴다 |
| 마지막에 안 보임 | **보이는 동안 방향을 맞춰놓고** 그대로 들어간다 |
| 관성으로 더 감 | **일찍 멈추고 다시 잰다.** 하나의 숫자로 안 박는다 |
| 삐뚤게 달림 | **정답 자세 한 번 기록.** 모든 상수 오차가 상쇄된다 |
| 회전이 좌우를 움직임 | **회전 중심을 잰다.** 확정 전엔 5도로 제한 |
| 통로 밖에서 시작 | **사이드스텝 한 번**, 그 뒤엔 중간점 계획 (3-2). 반복하지 않는다 |
| 마지막에 진입 조건이 안 됨 | 고치기 ≤ 5회 · 120초. **후진은 한 번, 최후의 보루.** 그래도 안 되면 사람 (3-9) |

한 줄로: **틀릴 수 있다는 걸 인정하고, 자주 고쳐 잡는다.**

### 8-0. CAN 드라이버는 신버전을 쓴다

`control_forklift_v2.py` 도 원래 광운대가 준 것인데 **구버전**이다.
새로 받은 폴더의 `calib/control.py` 가 최신이다.

**물리적으로 동일하다 — 기존 측정값이 살아남는다:**
```

MOV_PERIOD 10 ms · CTRL_PERIOD 5 ms · sync 0x0A
MOVEMENT_TEMPLATES  byte1=조향 · byte2=전후진 · 나머지 중립      ← 배치 동일
```

**신버전에만 있는 것 — 우리가 만들려던 게 다 들어 있다:**

| 기능 | 우리 계획 |
|---|---|

| `configure_motion_deadline` | 데드맨 |
| `configure_can_tx_observer` | TX 시각 기록 |
| `configure_can_enabled` | dry-run |
| **스레드 기반** (`CANBusOwner`) | **우리 스레드 구조와 맞는다. asyncio 불필요** |

```
807줄 (신)  vs  552줄 (구)
```

**동작 이름도 신버전을 따른다:**
```

rotate_right_slow  byte1 = 107      (구 rotate_cw 와 같은 값)
```

**강도는 광운대와 같게 — 회전 30 (byte1 157/97) · 전후진 60 (byte2 67/187).** (2026-09-30 결정 1·2)

             우리 9/7 실측 0.284 m/s 와 맞는다
97 (forward_slow)  →  안 쓴다. 그쪽 옛 FSM v3 의 잔재(`JOYSTICK_FORWARD_SLOW = 30  # FSM v3 visual-servo forward`,

### 8-2. 상수는 왜 그대로 쓰면 안 되나

**상수는 "값" 이 아니라 "그 차·그 센서·그 작업에서 나온 측정 결과" 다.**
식은 물리라 옮겨가지만 숫자는 안 옮겨간다.

| | 광운대 | 우리 |
|---|---|---|
| 센서 | YOLO 키포인트 (팔레트) | AprilTag |

## 9. 포크는 절대 안 건드린다

2026-09-07 에 회전 명령이 포크를 올린 사고가 있었다. byte4 가 리프트 축이었다.

**v4 는 직진·후진·제자리회전 여섯 개만 쓴다.** 포크·폴딩·리치는 이름조차 안 적는다.

### 2중 방어

```
① 이름 화이트리스트   stop · forward · forward_slow · backward
                      rotate_left_slow · rotate_right_slow          이 여섯만 쓴다 (forward_slow 는 검사만 하고 안 부른다 — 8-0)
② 동결 테이블        시작할 때 우리 값을 써넣고 6개 프레임의 8바이트를 전부 확인
                      byte1·byte2 외에 127 이 아닌 게 있으면 출발 거부
```

**②가 9/7 사고를 정확히 막는다.** 그때 사고는 **회전 명령이 byte4 를 쓴 것**이었고,
동결 테이블은 바로 그 바이트를 확인한다.
Dropbox 에 아직 **옛 버그 버전**(회전이 byte4/5 를 써서 포크가 올라감)이 있으니
시작할 때마다 확인한다.

> **포크 함수를 코드로 막지는 않는다.** 신버전에 `issue_command_lift_up` 같은 함수가
> 공개돼 있지만, 구버전에도 포크 경로는 있었고(키보드 `k`/`l`) **더 위험해진 게 아니다.**
> **우리가 안 부르면 그만이다.** 막는 코드는 과하다.

### 강도 이름 규칙 (광운대 규칙 그대로)

```python
JOYSTICK_FORWARD_SLOW = 30   # 강도 = 중립에서 밀어낸 양
AN_FORWARD_SLOW       = 97   # 바이트 = 실제로 나가는 값  (127 − 30)
```
**접두사가 구분자다.** v3 의 `FORWARD_SLOW = 30` 처럼 접두사 없는 이름을 만들지 않는다.

### 2026-09-21 검증 결과 (실제로 돌려봄)

```
주행 프레임 6종      b1·b2 외 전 바이트 127        통과
byte4(포크축)        6종 모두 정확히 127           통과
차단 시험 18건       정상 통과 / 위험 전부 차단     통과
출발 전 템플릿 검사                                통과
```

> 직진은 화면 켬/끔 차이가 3 mm 라 의미가 없다. **전용 A/B/C 비교 실험은 하지 않는다.**
> 대신 모드와 루프 주기를 매 세션 기록하고, `tools/history.py` 가
> "τ 가 모드와 상관있나" 를 자동으로 본다.
>
> 다만 **구조가 의도대로 동작하는지는 한 번 확인한다** —

### 12-0-1. 화면과 영상

### 12-2. 값이 들어가는 길

```

                                 끝나면 config 줄을 찍어 준다. --write 면 config/control.py 를 직접 고친다 ([calibrate <폴더>] 꼬리표)

- `CAM_YAW_OFFSET_DEG` 가 None 이면 **출발 거부** — 정면의 기준이라 없으면 못 맞춘다. 회전중심 None 이면 회전 상한 5도로 간다
- 조향 강도가 30 이 아니면 출발 거부 (씨앗이 30 짜리)
- σ 기준선을 못 내면(태그가 안 보임·두 해 헷갈림·차가 움직임) 정지·사람 — 조용히 기본값을 쓰지 않는다
