# Vehicle Dynamics Problem 해결 방법론

## 1. 목표

Vehicle Dynamics 문제의 핵심은 다음과 같다.

> **명령을 얼마나 오래 주었는지가 아니라, 현재 상태에서 해당 명령을 주었을 때 실제 차량이 어떻게 움직이고 최종적으로 어디에 멈추는지를 예측하는 것**

현재 시스템은 다음과 같은 고정식에 많이 의존하고 있다.

```text
1초 전진 ≈ 0.284 m
회전 명령 시간 → 예상 회전각
고정 STOP_LEAD
고정 ROT_LEAD_DEG
```

하지만 실제 지게차는 다음 이유로 같은 명령에도 매번 결과가 달라질 수 있다.

- 출발 반응 지연
- 정지 반응 지연
- 주행 중 속도 변화
- 정지 관성
- 회전 관성
- 바닥 마찰
- 적재 상태
- 배터리 / 모터 상태
- 조향 상태
- 센서 및 통신 지연

따라서 Vehicle Dynamics 문제는 단순한 고정식 보정이 아니라,

```text
현재 상태
+
현재 속도 / 각속도
+
최근 가속도 / 각가속도
+
명령
↓
실제 최종 이동 / 회전 결과 예측
```

구조로 바꾸는 것이 목표이다.

---

# 2. 전체 구조

Vehicle Dynamics는 크게 두 부분으로 나눈다.

```text
1. Straight Dynamics
2. Rotation Dynamics
```

그리고 각 부분에서 다음 두 문제를 해결한다.

```text
A. 명령 → 실제 이동량
B. Stop → 최종 정지 오차
```

---

# 3. Straight Dynamics

## 3.1 기존 문제

기존:

```text
목표 거리
↓
주행 시간 계산
↓
Forward
↓
sleep()
↓
Stop
```

이 방식은 명령 시간과 실제 이동량이 항상 일정하다는 가정을 포함한다.

하지만 실제로는 다음처럼 달라질 수 있다.

```text
2.0초 명령

Trial 1 → 0.551 m
Trial 2 → 0.542 m
Trial 3 → 0.559 m
Trial 4 → 0.548 m
```

따라서 `command duration → displacement` 관계를 실제 차량 기준으로 다시 측정해야 한다.

---

## 3.2 Straight Command Model

먼저 대략적인 이동량 모델을 만든다.

\[
distance = f(command\_duration)
\]

초기에는 다음 정도면 충분하다.

- Piecewise linear
- Polynomial
- Simple regression

이 모델은 최종 정밀 제어용이 아니라,

> **대략 어느 정도 명령을 줘야 목표 근처까지 갈 수 있는지**

를 계산하는 역할이다.

---

## 3.3 Stopping Distance Model

실제 정밀도를 결정하는 핵심은 Stop 이후 추가 이동거리이다.

\[
d_{stop}
=
forward_{stop\ command}
-
forward_{final}
\]

이 값을 현재 속도와 연결한다.

\[
d_{stop}=g(v)
\]

예:

| Stop 시 속도 | Stop 후 추가 이동거리 |
|---:|---:|
| 0.05 m/s | 0.012 m |
| 0.10 m/s | 0.028 m |
| 0.15 m/s | 0.050 m |
| 0.20 m/s | 0.076 m |

즉 controller는 단순히 목표까지의 거리만 보는 것이 아니라,

```text
남은 거리
vs
예상 정지거리
```

를 비교해야 한다.

---

# 4. 명령 지연

명령 지연은 다음처럼 나눌 수 있다.

## 4.1 Start Delay

```text
Forward command
→ 실제 motion 시작
```

사이의 시간.

---

## 4.2 Stop Delay

```text
Stop command
→ 실제 감속 시작
```

사이의 시간.

---

## 4.3 Inertial Motion

감속 이후 완전히 정지하기까지의 추가 이동.

---

## 중요한 점

초기 개발에서는 세 값을 완벽하게 분리할 필요는 없다.

더 중요한 것은

```text
Command
→ Final Result
```

를 직접 측정하는 것이다.

즉,

\[
command\ duration \rightarrow actual\ displacement
\]

그리고

\[
stop\ command \rightarrow additional\ displacement
\]

를 우선 확보한다.

---

# 5. 선형 가속도 활용

IMU linear acceleration은 위치 직접 계산보다 **동역학 상태 파악**에 사용하는 것이 좋다.

---

## 5.1 실제 출발 감지

예:

```text
10.000 s → Forward command
10.180 s → acceleration 변화 시작
```

이를 통해 start delay를 추정할 수 있다.

---

## 5.2 실제 감속 시작 감지

예:

```text
12.000 s → Stop command
12.140 s → negative acceleration 시작
```

이를 통해 stop response delay를 볼 수 있다.

---

## 5.3 완전 정지 판별

다음을 함께 사용한다.

```text
AprilTag velocity ≈ 0
+
IMU acceleration 안정
+
position 변화 거의 없음
↓
Vehicle stopped
```

---

## 5.4 정지거리 모델 개선

초기:

\[
d_{stop}=g(v)
\]

필요하면:

\[
d_{stop}=g(v,a)
\]

로 확장한다.

즉 같은 속도라도 최근 감속 패턴에 따라 정지거리가 다르면 가속도 정보를 추가한다.

---

# 6. IMU 가속도로 위치를 직접 구하지 않는 이유

이론상:

```text
acceleration
→ integrate
velocity
→ integrate
position
```

이 가능하지만, 실제 IMU bias 때문에 drift가 빠르게 누적된다.

따라서 역할을 다음처럼 나눈다.

```text
AprilTag
→ 절대 위치 기준

IMU acceleration
→ motion 변화 감지
→ 감속 상태
→ 정지 판별

IMU gyro
→ 회전속도
→ 회전 동역학
```

---

# 7. Rotation Dynamics

회전도 직진과 같은 방식으로 다룬다.

기존:

```text
목표 각도
↓
회전 명령
↓
고정 ROT_LEAD_DEG만큼 미리 Stop
```

개선:

```text
현재 heading
+
현재 yaw rate
+
현재 angular deceleration
↓
지금 Stop하면 추가로 몇 도 회전할지 예측
↓
Stop 시점 결정
```

---

# 8. Angular Velocity 활용

IMU gyro를 통해 현재 yaw rate를 얻는다.

\[
\omega = yaw\ rate
\]

정지 이후 추가 회전량을

\[
\theta_{stop}=h(\omega)
\]

형태로 모델링한다.

예:

| Stop 시 yaw rate | 추가 회전 |
|---:|---:|
| 2 deg/s | 0.3° |
| 4 deg/s | 0.6° |
| 6 deg/s | 1.0° |
| 8 deg/s | 1.5° |

이렇게 하면 고정 `ROT_LEAD_DEG`보다 상황에 맞게 보정할 수 있다.

---

# 9. Angular Acceleration 활용

각가속도:

\[
\alpha
\approx
\frac{\omega_t-\omega_{t-1}}{\Delta t}
\]

를 계산할 수 있다.

역할:

- 회전 시작 감지
- 회전 감속 시작 감지
- Stop 이후 yaw rate 감소 패턴 확인
- 회전 정지거리 예측 개선

필요하면:

\[
\theta_{stop}=h(\omega,\alpha)
\]

형태로 확장한다.

---

# 10. Rotation Command Model

대략적인 회전 명령 모델:

\[
\Delta\theta = f(command\ duration)
\]

역할:

```text
큰 각도 회전
→ 대략적인 command 생성
```

정밀 Stop은 별도로

\[
\theta_{stop}=h(\omega)
\]

를 사용한다.

즉 큰 이동은 command model,
정밀 정지는 stopping model이 담당한다.

---

# 11. 저속 Final Approach

정밀 docking에서는 마지막 구간의 속도를 낮추는 것이 매우 중요하다.

속도가 낮아지면:

- 정지거리 감소
- 정지거리 variance 감소
- command delay 동안 추가 이동 감소
- perception latency error 감소
- overshoot 감소

따라서:

```text
Far Zone
→ Normal speed

Near Zone
→ Reduced speed

Final Zone
→ Very low speed
→ Real-time stop prediction
```

구조를 권장한다.

회전도 마찬가지이다.

```text
Large heading error
→ normal rotational speed

Small heading error
→ low rotational speed
```

# 15. Perception과 연계

Vehicle Dynamics 모델은 Perception의 출력값을 사용한다.

```text
Perception
↓
Current forward
Current velocity
Current heading
Current yaw rate
↓
Vehicle Dynamics
↓
Predicted Final Pose
```

즉 Vehicle Dynamics는 단독으로 동작하지 않는다.

# 16. Controller와 연계

Vehicle Dynamics의 최종 출력은 다음이다.

```text
"지금 이 명령을 주면
최종적으로 어디에 멈출 것인가?"
```

Controller는 이 예측값과 목표를 비교해 다음 명령을 결정한다.

```text
Current State
+
Dynamics Prediction
+
Target
↓
Next Command
```

# 핵심 결론

Vehicle Dynamics 문제의 핵심은:

1. **명령 시간과 실제 이동 결과를 분리한다.**
2. **Stop 이후 추가 이동/회전을 별도 모델로 만든다.**
3. **현재 속도와 yaw rate를 정지 예측에 사용한다.**
4. **가속도와 각가속도는 motion 변화와 정지 특성 파악에 사용한다.**
5. **마지막 구간은 저속으로 접근해 불확실성 자체를 줄인다.**

궁극적으로는

```text
"몇 초 움직일까?"
```

가 아니라

```text
"지금 명령하면 최종적으로 어디에 멈출까?"
```

를 계산하는 시스템으로 바꾸는 것이 목표이다.
