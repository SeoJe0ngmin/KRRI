| Substack (2026, Orin Nano JP6.2.2) | V4L2 + HID 모듈 재빌드 | RSUSB Orin 프리즈·드롭 보고(2차), 재빌드 후 199.8 Hz σ 0.12 ms |
| 2.58.2 릴리스 | (V4L2 보강) | JP6 USB3 메타데이터 누락 수정 |

- 근거 요약: (1) 소스 코드상 모션 모듈(HID) 타임스탬프 리더는 비디오와 같은 `global_timestamp_reader`·`time_diff_keeper` 로 감싸져 있고 백엔드 분기가 없으며, Intel(ev-mp) 이 RSUSB 에서 IMU HW/global ts 가 나온다고 확답 → **RSUSB 에서 모션 global_time 매핑은 가능**(VM 관측과 일치). 단 도메인은 (옵션 ON ∧ 첫 동기 샘플 ∧ HW_CLOCK) 일 때만 GLOBAL 이고 시작 직후엔 HARDWARE_CLOCK 이 정상이며, 실패 모드(메타 누락→SYSTEM_TIME, IMU 수 초 오프셋→initial_reset 필요, 71.6 min 랩 역행→2.58.4 전 미수정) 가 문서화되어 있다. realsense-ros 는 어느 경우도 거부하지 않고 도메인별 폴백+리셋 감지로 처리한다. (2) get_timestamp() 는 노출중심이 아니라 **USB 전송 시작 시각**(depth 예시에서 노출중심과 37 ms 차) — 캡처 시각은 SENSOR_TIMESTAMP(컬러에 등록됨, HW 클록) 로 되돌려 잡아야 하고, 자이로는 SENSOR_TIMESTAMP 가 없다. (3) D435 RGB T_Line=30 µs(지원엔지니어 진술) → 1080p readout ≈ 32 ms ≈ 프레임주기; 화면 중앙 태그는 기준행 대비 ~16 ms 결정론적 오프셋, 태그 내부 skew 1–4 ms. D400 global_time 의 정확도 수치는 Intel 이 공개한 것이 없다(T265 만 "millisecond accurate").
- 판정 도움: **제3안 쪽.** "assert 실패 → 출발 거부" 는 코드 동작(ready 전 HARDWARE_CLOCK 과도구간, #4505 첫 15 s) 과 충돌하고, realsense-ros·PR #3909 의 관행은 "GLOBAL 대기(타임아웃) → 안 되면 도메인별 폴백 + 런타임 타당성 검사(|global_ts − host_now|, 역행 감지) + 세션 시작 hardware_reset". ε 는 15 ms(critic) 가 물리적으로 타당(7°/s×15 ms=0.1°, 0.3 m/s×15 ms=4.5 mm; Intel 자체 동기 샘플 거절 임계도 15 ms) 하나 **롤링셔터 중앙행 오프셋 ~16 ms 는 ε 에 "흡수"되지 않고 ε 를 넘는 상수 바이어스** → 행×30 µs 로 결정론 보정 후 15 ms 를 지터 한도로 두는 것이 문헌과 맞고(proposer 의 30 ms 는 보정 없이 바이어스를 삼키는 안), 어느 행 기준인지는 실측으로 확정해야 한다.
- 문헌 없음 — 실차/VM 실험으로 결정해야: (a) D400 global_time 정확도·VM USB 패스스루 왕복 지터 → 시작 후 컬러·자이로 각각 `TOA − get_timestamp()` 분포와 도메인 GLOBAL 전환 시각 로깅(2.58.4+ 면 `rs2_get_device_time_ms` 왕복 직접 측정); (b) 컬러 SENSOR_TIMESTAMP 존재 여부·FRAME−SENSOR 차·기준 행 → AE ON/OFF 각각 `supports_frame_metadata` + 회전 중 자이로 적분 vs 태그 β 변화 상호상관으로 카메라–자이로 오프셋 추정(Kalibr 식); (c) IMU 샘플 타임스탬프의 물리적 의미(센서 샘플 시각 vs FW 패키징) → 같은 상호상관 실험의 잔차로 판단; (d) 2.56.5 랩 역행 → 세션 전 `hardware_reset` 후 60 min 이내 운용 또는 71.6 min 연속 스트림 테스트 1회.
