- 근거 요약: (1) CAN 프레임 ID 만으로 노드 구성은 표준식으로 읽힌다 — 0x1E3/0x2E3 = 노드 0x63 의 TPDO1/2(리모컨 수신기 형식과 일치), 0x764 = 노드 0x64 의 heartbeat 슬롯이며 우리가 보내는 데이터 0x00 은 규격상 boot-up 이다. (2) 워치독 소실 시 "중립 정지" 는 **표준이 보장하지 않는다**: CiA 기본은 Pre-operational 전이(PDO 무시)까지이고 물리 반응은 장치별, Curtis 는 스로틀 0%+래치(NMT/키), Sevcon 은 500 ms 후 등급 설정에 따라 경고~drive inhibit, Zapi 는 경고+속도 컷백 사례가 있어 **세 제조사가 서로 다르고 OEM 설정으로 더 갈린다**. (3) 동일 ID 이중 송신에 중재 규칙은 없고 비트오류→bus-off(비결정적) 또는 데이터 동일 시 잠복 성공이며, ACK/오류프레임/오류카운터/bus-off 는 canlib 에서 관측 가능하나 "적용 여부" 는 관측 불가.
- 판정 도움: **judge(보류) 쪽을 문헌이 지지** — 차량 워치독 유무·T_wd·래치·복구는 제조사·OEM 설정 의존이라 문헌으로 확정 불가, precheck (1) 없이는 어떤 실주행도 안전 근거가 없다는 판단이 맞다. 단 critic 의 "소프트웨어로 못 본다" 는 절반만 맞다(버스 계층은 canlib 로 관측 가능, 물리 적용만 불가) → FM9 감지기는 canlib 상태+카메라/IMU 속도 이중으로 설계할 근거가 있다. proposer 가 T_wd 를 상수로 두려 했다면 근거 없음 — 실측값이어야 한다.

**문헌 없음 — 실차 실험으로 결정해야** (아래는 문헌이 답하지 못한 항목과 그 측정 제안)
- 이 차량의 T_wd·래치·복구(FM9): ① 키온 상태에서 Kvaser **listen-only(silent)** 60 s 캡처 → 버스에 이미 0x1E3/0x2E3/0x764 가 있는지, 0x7xx heartbeat 로 노드 목록, 0x08x EMCY, 컨트롤러 TPDO 존재·주기 확인(리모컨 켬/끔 두 번). ② 차체 고정·안전구역에서 forward 97 송신 중 **0x764 만 중단**(0x1E3 유지) → 카메라/IMU 로 속도 소멸까지 시간 = T_wd,hb, EMCY·heartbeat 상태 변화 기록; **0x1E3 만 중단** → T_wd,pdo; 둘 다 중단. 잔류 속도(Zapi 형 컷백) 여부 기록. ③ 각 타임아웃 뒤 복구 조건을 순서대로 시험: 프레임 재개만 / stop(127) 홀드 후 / 0x2E3 driving_mode 재송신 후 / NMT Start(0x000 [01 63], [01 64]) 후 / 키 사이클 → 래치 분류. ④ 리모컨 수신기 전원 켠 채 PC 가 동일 중립 프레임 송신 → 오류프레임·오류카운터 확인, 이어 다른 데이터 → bus-off 도달 시간·어느 노드가 죽는지 → "수신기 반드시 차단" 규칙 근거. ⑤ heartbeat 데이터 0x05 vs 0x00 수용 차이. 산출: T_wd 두 값, 래치 유형, 복구 시퀀스 — 전부 실측(새 config 상수 0).
- ISO 3691-4 / EN 1175 / EN 13557 의 "통신 소실 시 정지 시간" 조항: HTML 요약에서 원문 확인 실패, 표준 PDF 는 이 환경에서 미열람 → 인용 불가(수치 0.55 s/2 s 등은 검증되지 않아 싣지 않음). 과제 문서에 넣으려면 표준 원문 확보 필요.
- FM1 직진 다리 문턱(≥1 m, 드리프트 ≥2°)·태그 2 의 h≈0 pitch-cue 소멸·9/7 프레임별 bag 존재 여부: 문헌 문제가 아님 — b floor 실측(정적 R(d,φ) 실험) 후 확정, bag 은 `work_dirs/` 실물 확인.
