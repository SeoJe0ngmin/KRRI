- **근거 요약**: (1) 리모컨·차량측 프로토콜 문서(하트비트 타임아웃 ms, movement 끊김 시 동작, 0x80 의미·해제 절차) 는 공개 문헌·리포 어디에도 없음 — "250 ms" 는 코드 주석의 전언. (2) 규범은 일관됨: 무선제어 링크는 유효신호 부재 **≤0.5 s** 에 자동 정지(IEC 62745), 통신 재확립·e-stop 리셋은 **재시동시키지 않음**(IEC 62745·ISO 13850). 그러나 우리는 수신기 뒤 CAN 에 주입하므로 실제 걸리는 것은 차량 컨트롤러의 PDO/heartbeat 타임아웃이고, 그 값·동작(정지/마지막 명령 유지/스로틀 컷 vs 브레이크)은 **통합업체 설정**(Curtis: 0 이면 무한 유지; Sevcon 기본 500 ms) 이라 문헌으로 결정 불가. (3) ID 구조가 CANopen 과 일치해 RX 스니핑·SDO 읽기라는 저비용 확인 경로가 있음(가설). (4) 데드맨은 실험 결과와 무관하게 송신측에 두는 것이 로봇 스택 표준(0.5~1 s).
- **판정 도움**: judge 의 보류 사유를 문헌이 지지 — "차량 워치독 미확인 → 실차 실험" 이 맞고, **데드맨은 실험 결과와 독립적으로 필수**(7-7). emergency 시험은 표준상 래치+별도 재시동이 기본 가정이므로(7-1·7-3·7-5 KSI 사이클) **정지 상태·사람 제동 위치·복구 절차 미지 전제** 가 타당. "외부 σ ≤ T_f/3" 은 자리만 두는 것이 맞음(T_f 는 측정값). 반복 횟수는 7-9 로 정량화 가능(셀당 10~20 이면 percentile 은 정규 k-factor 또는 셀 통합으로만).
- **문헌 없음 — 실차 실험으로 결정해야**(precheck 에 넣을 항목):
  1. **워치독 매핑**(정지 → 97 크립, 사람 제동): heartbeat 만 끊기 / movement 만 끊기 / control(0x2E3) 만 끊기 / 전부 끊기(busOff) × 각 ≥3회, 마지막 프레임 **TXACK 시각** vs 카메라·IMU 감속 개시 → T_f 또는 "유지". 추가: 0x2E3 byte4 카운터를 고정한 채 반복 송신(동일 프레임 재생) — 카운터 정지를 신호 상실로 보는지.
  2. **끊김 정지 vs 명시적 stop 프레임 정지의 감속 프로파일** 비교(스로틀 컷=회생 중립 vs 브레이크; Curtis 72/77 구분).
  3. **복구**: 각 끊김 후 프레임 재개만으로 재출발되는지 / driving_mode+heartbeat 버스트 필요 / 키 사이클 필요 → 래치 여부 기록.
  4. **0x80 emergency**: 정지 상태에서 burst → 'M'(0x42 복귀) → forward_slow 시도 → 불응이면 버스트 → 키 사이클 순으로 해제 절차 확정. 주행 중 시험은 정지 시험 뒤에만.
  5. **RX 스니핑**(Kvaser 수신 + TXACK 켜기): 차량측 프레임(EMCY 0x080+n, heartbeat, 상태 PDO) 존재 확인; 있으면 SDO 로 0x1016/0x1017 읽기 시도 — 성공 시 T_f 직접 확보.
  6. 데드맨 구현 확정값은 위 T_f 와 무관하게 송신측 0.3~0.5 s(7-7 관행) 로 두고, T_f 가 측정되면 "외부 σ ≤ T_f/3" 채움.
