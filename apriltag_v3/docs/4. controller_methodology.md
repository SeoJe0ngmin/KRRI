# Controller Problem 해결 방법론

## 1. 목표

현재 Controller 문제의 핵심은 다음과 같다.

> **Lateral과 heading을 독립적으로 반복 보정하면서 서로 영향을 주기 때문에 correction이 계속 반복되는 구조**

예:

```text
Heading 보정
→ Lateral 변화

Lateral 보정
→ Heading 변화

다시 Heading 보정
→ 다시 Lateral 변화
```

이 때문에 작은 오차에도 반복적인 correction이 발생한다.

최종 목표는

```text
lateral
heading
forward
```

을 각각 따로 맞추는 것이 아니라,

> **현재 vehicle pose 전체를 보고 목표 pose에 가장 잘 접근하는 다음 motion을 결정하는 것**

이다.

---

# 2. 현재 Controller 구조의 문제

현재 구조는 개념적으로 다음에 가깝다.

```text
Heading error 확인
↓
회전

다시 측정

Lateral error 확인
↓
보정

다시 측정

Heading 다시 확인
↓
재보정
```

이 방식은 각 오차를 독립적으로 다룬다는 점이 문제이다.

---

# 3. Lateral과 Heading Coupling

Lateral과 heading은 독립적인 상태가 아니다.

특히 회전중심이 존재하는 차량에서는 heading을 바꾸면 위치도 함께 바뀐다.

현재 시스템에는 예를 들어:

```text
CAM_TO_PIVOT ≈ 1.46 m
```

와 같은 offset이 존재한다.

따라서 작은 회전도 실제 pivot / camera 위치를 변화시킨다.

즉:

\[
\Delta heading
\Rightarrow
\Delta lateral
+
\Delta forward
\]

가 발생한다.

반대로 lateral을 맞추기 위한 움직임도 heading에 영향을 줄 수 있다.

---

# 4. Controller 입력 기준 통일

Controller는 camera raw pose를 직접 받지 않고,

```text
pivot_forward
pivot_lateral
pivot_heading
```

을 받는다.

즉 모든 제어 판단을 실제 차량 회전중심 기준으로 통일한다.

Perception에서 이미 pivot frame으로 변환된 상태를 받는 것이 좋다.

---

# 5. Pose Error Vector

Controller는 다음과 같은 전체 pose error를 하나의 벡터로 본다.

\[
e =
\begin{bmatrix}
e_{forward}\\
e_{lateral}\\
e_{heading}
\end{bmatrix}
\]

기존:

```text
heading만 먼저
lateral 따로
forward 따로
```

개선:

```text
현재 전체 pose error
↓
다음 motion 선택
```

---

# 6. 단일 축 Correction에서 Pose Correction으로

기존:

```text
if heading error:
    rotate()

if lateral error:
    lateral correction()
```

개선:

```text
current pose
+
target pose
+
vehicle kinematics
↓
which motion reduces total pose error most?
```

즉 한 번의 motion이 전체 pose에 어떤 영향을 미치는지 고려한다.

---

# 7. 작은 Correction을 반복하는 Closed-loop 구조

한 번의 correction으로 완벽하게 맞추려고 하면 dynamics 오차 때문에 overshoot가 발생할 수 있다.

따라서 다음 구조가 좋다.

```text
작은 motion
↓
실시간 perception
↓
pose error update
↓
다음 작은 motion
```

즉:

```text
Predict
→ Move
→ Observe
→ Correct
```

의 반복이다.

단, "반복" 자체를 없애는 것이 아니라

> **서로 싸우는 반복 보정이 아니라 목표로 수렴하는 반복 제어**

로 바꾸는 것이 핵심이다.

---

# 8. Deadband를 크게 늘리지 않고도 안정화하는 방법

정확도가 높아야 하므로 단순히 tolerance를 넓게 줄 수 없다.

대신 controller가 correction을 시작하는 조건에 **신뢰도와 예상 효과**를 같이 넣는다.

예:

```text
Estimated lateral error = 8 mm
Uncertainty = ±15 mm
```

이면 correction을 바로 하지 않는다.

반대로:

```text
Estimated lateral error = 18 mm
Uncertainty = ±3 mm
```

이면 correction한다.

즉 단순 threshold가 아니라

```text
error magnitude
+
state uncertainty
```

를 같이 사용한다.

---

# 9. Correction Priority

모든 구간에서 동일한 우선순위를 사용할 필요는 없다.

예를 들어:

## Far Zone

```text
Forward progress 우선
Heading 대략 정렬
```

## Near Zone

```text
Heading + Lateral 동시 고려
```

## Final Zone

```text
Final pose accuracy 우선
Very small motion
```

즉 distance에 따라 controller mode를 나누는 것이 좋다.

---

# 10. Zone-based Controller

예:

```text
Zone 1: Far
Zone 2: Near
Zone 3: Final
```

---

## Zone 1 - Far

목적:

```text
빠르게 목표 근처 접근
```

특징:

- 큰 motion 허용
- 정밀 correction 최소화
- 대략적인 heading 정렬

---

## Zone 2 - Near

목적:

```text
pose error 줄이기
```

특징:

- speed 감소
- heading / lateral coupling 고려
- dynamics model 사용

---

## Zone 3 - Final

목적:

```text
최종 pose 정밀 수렴
```

특징:

- 매우 낮은 속도
- 작은 correction
- 실시간 perception
- stopping prediction 사용
- uncertainty 확인 후 command

---

# 11. Heading Correction 시 Lateral 영향 예측

회전 명령을 주기 전에,

```text
현재 heading error
↓
회전하면 lateral이 얼마나 변할지
```

를 예상해야 한다.

즉 단순히

```text
heading error = 2°
→ 2° 회전
```

이 아니라,

```text
2° 회전
→ pivot / camera geometry상
lateral이 몇 mm 변하는가?
```

를 같이 본다.

이렇게 하면 heading을 맞춘 뒤 lateral이 크게 틀어지는 상황을 줄일 수 있다.

---

# 12. Lateral Correction 시 Heading 영향 고려

마찬가지로 lateral correction motion이 heading을 변화시키는 구조라면,

```text
lateral error correction
↓
predicted heading change
```

도 같이 계산한다.

즉 모든 command를

\[
\Delta x = f(x,u)
\]

형태로 본다.

여기서:

- \(x\): current pose
- \(u\): command
- \(\Delta x\): command 이후 pose 변화

이다.

---

# 13. Vehicle Dynamics와 Controller 연결

Controller는 고정식이 아니라 Vehicle Dynamics의 prediction을 사용한다.

예:

```text
Current State
+
Candidate Command
↓
Vehicle Dynamics Model
↓
Predicted Final Pose
↓
Target과 비교
```

그 다음 가장 좋은 command를 고른다.

---

# 14. 간단한 Candidate-based Controller

MPC까지 바로 가지 않고도 다음처럼 시작할 수 있다.

후보 command:

```text
small forward
medium forward
small left rotation
small right rotation
stop
```

각각에 대해 Vehicle Dynamics로 최종 pose를 예측한다.

그리고 비용함수:

\[
J =
w_f e_f^2
+
w_l e_l^2
+
w_h e_h^2
\]

를 계산한다.

가장 \(J\)가 작은 command를 선택한다.

이렇게 하면 lateral / heading / forward를 하나의 기준으로 같이 볼 수 있다.

---

# 15. 가중치의 의미

예:

\[
J =
w_f e_f^2
+
w_l e_l^2
+
w_h e_h^2
\]

여기서:

- \(w_f\): forward 중요도
- \(w_l\): lateral 중요도
- \(w_h\): heading 중요도

Final Zone에서는 lateral / heading 가중치를 높일 수 있다.

Far Zone에서는 forward progress를 더 중요하게 볼 수 있다.

---

# 16. MPC로의 확장

더 발전시키면 Model Predictive Control(MPC) 형태로 확장 가능하다.

현재 상태에서 한 command만 보는 것이 아니라,

```text
command 1
→ predicted state 1
→ command 2
→ predicted state 2
→ ...
```

여러 step을 미리 예측한다.

하지만 초기 구현부터 MPC를 적용할 필요는 없다.

먼저:

```text
1-step candidate evaluation
```

으로 시작하는 것이 좋다.

---

# 17. Oscillation 방지

반복 보정이 생기는 이유 중 하나는 작은 error 변화에도 command 방향이 쉽게 바뀌기 때문이다.

이를 줄이기 위해 다음을 사용할 수 있다.

- Hysteresis
- Minimum command interval
- Minimum expected improvement
- State uncertainty check

예:

```text
이번 correction으로 예상 개선량 < threshold
→ command하지 않음
```

즉 "조금 틀렸으니 무조건 움직인다"가 아니라

> **움직였을 때 실제로 pose가 좋아질 가능성이 충분한지**

를 판단한다.

---

# 18. Command Reversal 방지

예:

```text
Left correction
→ Right correction
→ Left correction
→ Right correction
```

같은 ping-pong을 막기 위해 최근 command history를 사용한다.

예:

```text
직전 command와 반대 방향 command가 필요하면
→ 충분한 error 변화가 있을 때만 허용
```

이렇게 하면 measurement noise 때문에 command가 계속 뒤집히는 것을 줄일 수 있다.

---

# 19. Perception Uncertainty 활용

Perception에서 다음 값을 넘기는 것이 좋다.

```text
forward_uncertainty
lateral_uncertainty
heading_uncertainty
```

Controller는 error뿐 아니라 uncertainty도 본다.

예:

```text
error = 10 mm
uncertainty = 15 mm
→ 기다림

error = 10 mm
uncertainty = 2 mm
→ correction
```

---

# 20. Final Pose Acceptance

정확도가 높아야 하므로 단순히 큰 deadband를 사용하지 않는다.

대신 최종 성공 조건을 다음처럼 구성할 수 있다.

```text
|forward error| < threshold
|lateral error| < threshold
|heading error| < threshold
+
uncertainty sufficiently small
+
vehicle fully stopped
```

즉 단순 pose 값뿐 아니라 measurement confidence와 정지 상태를 함께 본다.

---

# 21. Controller 사전 실험

별도 script를 두는 것도 좋다.

예:

```text
tools/precheck_controller_response.py
```

실험 내용:

```text
small forward command
small rotation left
small rotation right
```

각 command가 실제로

```text
Δforward
Δlateral
Δheading
```

을 얼마나 만드는지 측정한다.

이 데이터는 controller의 candidate prediction과 coupling model에 사용한다.

---

# 22. Controller Response Map

예:

| Command | ΔForward | ΔLateral | ΔHeading |
|---|---:|---:|---:|
| Small Forward | +50 mm | +2 mm | +0.1° |
| Small Left Rot | -3 mm | +18 mm | +1.0° |

이런 표를 만들면

```text
"heading correction이 lateral에 얼마나 영향을 주는지"
```

를 실제 데이터로 볼 수 있다.

# 핵심 결론

Controller 문제의 핵심은 다음과 같다.

1. **Lateral과 heading을 독립적으로 보지 않는다.**
2. **모든 pose를 forklift pivot 기준으로 통일한다.**
3. **한 command가 전체 pose에 미치는 영향을 예측한다.**
4. **큰 correction 한 번보다 작은 closed-loop correction으로 수렴한다.**
5. **오차 크기뿐 아니라 uncertainty와 예상 개선량을 함께 본다.**
6. **최종적으로 candidate-based predictive controller → MPC로 확장 가능하다.**

궁극적으로는

```text
"heading 맞추고 lateral 맞추기"
```

가 아니라

```text
"현재 전체 pose에서 목표 pose로 가장 잘 수렴하는 다음 motion을 선택하기"
```

로 controller 구조를 바꾸는 것이 목표이다.
