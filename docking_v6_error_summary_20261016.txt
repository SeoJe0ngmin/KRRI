Docking v6 실험 오류 정리
실험일: 2026-10-16 / 정리일: 2026-10-19
기준: 채팅에 공유된 실행 로그와 실험 결과. 해결 여부는 현장에서 확인된 범위까지만 표시함.

1. 전체 요약

기존 태그 중심 주행에 RGB·IR·IMU와 OpenVINS, ROS 2 연결, 보정 및 통신 감시 기능을 추가하면서 설치 환경, 센서 시간 동기화, 좌표계, 초기 보정, CAN 통신 문제가 연속해서 발생했다.
카메라 영상과 OpenVINS 위치 출력은 이후 정상 동작하는 구간을 확인했고, CAN으로 보정용 3초 전진도 수행했다. 그러나 초기 보정 과정에서 추적 기준이 끊기거나 정지 관측 부족으로 저장이 거부되어, 최종 자동 도킹 완료와 정확도 개선은 확인하지 못했다.
단순히 하드웨어 성능이 부족했던 것으로 단정할 수 없다. 연결 코드의 예외 처리와 보정 조건, 실제 CAN 오류가 함께 나타났다.

2. 연결 및 설치 환경

2-1. 원격 데스크톱
- gnome-remote-desktop 서비스는 active, RDP server started였으나 접속 문제는 지속됐다.
- TPM 초기화 실패 후 GKeyFile로 대체한다는 로그가 있었다. 이것만으로 접속 실패 원인을 확정할 수는 없다.
- 사용자가 VS Code/SSH 사용으로 전환하여 원격 데스크톱 문제는 보류했다.

2-2. 시스템 시간 초기화
- 로그 폴더가 19700101로 생성되는 현상이 반복됐다.
- Mac 시간을 SSH로 전달해 시간을 맞춘 적이 있으나, 이후에도 초기 날짜 로그가 나타났다.
- 시스템 시각 문제와 센서 자체 타임스탬프 이상은 별도로 구분해야 한다.

2-3. 코드 업데이트 및 실행 위치
- No module named docking.imu_diagnostic: 해당 파일이나 실행 경로·환경이 맞지 않는 상태에서 발생했다. 이후 파일 존재와 정상 실행을 확인했다.
- Mac 전용 /Users/... 업데이트 명령과 Jetson의 /home/jetson/... 실행 경로를 혼동하는 문제가 있었다.
- 실행 중인 측정 프로세스 때문에 업데이트 스크립트가 복사를 차단한 적이 있었다. 프로세스 종료 후 업데이트가 필요했다.
- 터미널에 Markdown의 ```bash까지 붙여 넣어 > 입력 대기 상태가 발생했다. 명령문만 입력해야 한다.

2-4. 네트워크 및 패키지 설치
- apt 저장소 연결에서 Ign 및 Connecting 상태가 반복돼 설치가 진행되지 않았다.
- libopencv-dev는 NVIDIA 저장소 4.8 후보, 일부 OpenCV 개발 패키지는 Ubuntu 4.6 설치 상태로 나타나 패키지 버전 조합을 정리해야 했다.
- ModuleNotFoundError: No module named 'cv2'가 발생했다. 실제 실행 가상환경에 OpenCV가 준비되지 않은 상태였다.
- 이후 docking-v6 환경에서 numpy, cv2, scipy, yaml, pupil_apriltags, pyrealsense2, rclpy, docking_v6_msgs import 성공을 확인했다.

2-5. ROS 패키지 설정 및 빌드
- package.xml의 maintainer@localhost가 유효하지 않은 이메일로 거부됐다.
- 재빌드 과정에서 이전 install 경로가 AMENT_PREFIX_PATH/CMAKE_PREFIX_PATH에 남아 경고가 발생했다.
- 이후 메시지 패키지와 docking_openvins 빌드는 완료됐다. 빌드 성공은 센서 연결이나 실제 주행 성공을 의미하지 않는다.

3. RealSense 카메라 및 IMU

3-1. 센서 외부 파라미터 조회 실패
- Requested extrinsics are not available 오류로 카메라 작업자가 종료됐다.
- 필요한 스트림 간 외부 파라미터 조회 및 스트림 준비 과정이 문제였으며, 이후 연결 부분을 수정했다.

3-2. 영상 수신 타임아웃
- video: Frame didn't arrive within 1000 오류가 반복됐다.
- 초기 영상 수신이 1초 안에 완료되지 않으면 바로 종료하는 문제가 있었다.
- 시작 대기와 운용 중 수신 감시를 구분하도록 조정했다. 이후 실제 영상 출력을 확인했다.

3-3. 센서 시각 역전 및 프레임 번호 이상
- sensor_clock_reversed 오류가 발생했다.
- stereo_sequence_invalid left: frame 5→0처럼 프레임 번호가 감소했지만 타임스탬프는 증가하는 사례가 있었다.
- 프레임 번호 이상과 실제 시간 역전을 구분할 필요가 있었다. 단순 번호 변화만으로 정상 영상까지 종료하지 않도록 처리 방향을 수정했다.
- 카운터 이상이 있으면 SDK 누락 프레임 집계의 신뢰성도 별도로 표시해야 한다.

3-4. 시작 시 IMU의 오래된 샘플 혼입
- imu_clock_or_sample_gap: accel의 device timestamp가 약 26초 증가했는데 host 도착 간격은 약 0.0019초인 사례가 있었다.
- 이때 paired_samples=0이었으므로 주행 중 26초 동안 IMU가 끊겼다고 해석하면 안 된다.
- 초기 샘플과 현재 샘플을 구분하고, 시작 시 안정된 시간 구간을 확보하도록 처리했다.

3-5. IMU 정지 보정 반복 실패
- motion_during_calibration, stationary_calibration_timeout, sample_gap 등이 발생했다.
- 초기 진단에서는 움직임 기준 0.5 deg/s를 초과한 샘플이 1,112개, 이후 더 안정된 측정에서도 156개였다.
- 포장 박스 위 고정 및 미세 흔들림, 센서 잡음이 정지 판정에 영향을 줄 수 있었다. 모든 실패를 실제 차량 이동으로 볼 수는 없다.
- 이후 일부 측정에서는 READY / stationary_bias_measured를 확인했다.

3-6. 갑자기 밝아진 영상
- IR 화면이 과노출처럼 하얗게 보이고 태그가 검출되지 않는 현상이 있었다.
- 당시 영상은 확인됐지만, 해당 스크린샷만으로 노출 설정·자동 노출 적응·환경광 중 원인을 확정할 수 없다.
- 영상 밝기 문제와 프로그램 종료 오류는 별개였다.

4. OpenVINS 및 위치 추정

4-1. 설정 파일 파싱 실패
- invalid_stereo_fej_configuration 오류가 발생했다.
- Tw, Ta, R_IMUtoACC, R_IMUtoGYRO 노드를 읽지 못한다는 로그가 있었다.
- OpenVINS가 요구하는 설정 형식과 생성 설정이 맞지 않아 프로세스가 종료됐다.

4-2. OpenVINS 출력 타임아웃
- OpenVINS process exited 및 OpenVINS output timeout이 반복됐다.
- camera worker stopped라는 상위 오류만 보여 실제 OpenVINS 실패 원인을 바로 파악하기 어려운 경우도 있었다.
- 초기화 지연, 입력 전달, 프로세스 종료를 구분하는 진단과 시작 처리가 필요했다.

4-3. 영상은 보이는데 odom=false
- 카메라 약 27 fps, processed_fps=0, odom=false 상태가 있었다.
- 영상 수신 성공과 OpenVINS의 유효한 위치 출력 성공은 서로 다른 단계다.
- 이후 openvins_initializing에서 openvins_corrected로 전환되고 처리 약 14~20 fps가 나오는 구간을 확인했다.

4-4. odom=true/false 반복
- 초기화 대기, 보정 출력 사이의 추적, 실제 위치 불연속을 구분할 필요가 있었다.
- openvins_tracking_between_updates는 보정 출력 사이를 추적하는 상태로 표시됐다.
- 반면 relative_pose_discontinuity는 상대 위치의 연속성 검사 실패이며, 마지막 실험에서도 반복됐다.
- 마지막 불연속의 근본 원인은 채팅 로그만으로 확정되지 않았다.

4-5. 추적 기준 재설정
- 보정 중 motion epoch가 바뀌어 시작점과 끝점을 같은 위치 기준으로 비교할 수 없다고 판단했다.
- 처음에는 재설정이 한 번이라도 있으면 전체 보정 저장을 거부했다.
- 이후 정차 구간의 추적 재설정과 실제 전진 구간의 재설정을 구분하도록 변경했다.
- 센서 시각 기준이 바뀌거나 전진 중 추적 기준이 끊긴 경우까지 무조건 연결해서 저장할 수는 없다.

5. 좌표계 및 카메라 장착 보정

5-1. 정면인데 heading이 약 -178도로 표시
- 차량은 태그 정면에 가까웠는데 heading이 -161도 또는 -178도로 나타났다.
- 태그 좌표계와 차량 접근 방향의 변환 문제가 있었으며, 컬러 카메라를 차량 중앙에 설치했다는 이유만으로 180도 뒤집히는 것은 아니다.
- 변환 수정 후 보정 보고서에서 yaw 약 2.66도를 확인했다.

5-2. heading 0을 미리 맞춰야 하는 초기 보정 방식
- 초기 mount 방식은 차량이 태그면 법선과 정렬돼 있다는 기준을 사용했다.
- 차량 자체가 비스듬한 상태에서는 그 각도를 카메라 장착 오차와 분리하기 어려웠다.
- 현장에서 정확히 heading 0을 맞추기 어려워 직진 관측을 이용한 보정 방식으로 변경했다.

5-3. 정지했는데 visual_stationarity_not_confirmed
- 태그가 286회 모두 수락되고 정지 비율이 약 96.2%인 측정에서도 저장이 거부됐다.
- 해당 보고서는 각도 분산 약 0.214도, 전후반 변화 약 0.046도, 위치 분산 약 1.44 mm였다.
- 센서가 전혀 안정되지 않은 상황으로 보기 어려웠으며, 정지 판정과 저장 조건의 연결을 점검해야 했다.

5-4. 고정 정지 허용치가 진동과 충돌
- 위치 4 mm, 각도 0.35도 같은 단순 기준은 제자리 진동에도 정지 실패를 만들 수 있었다.
- 제자리 흔들림과 지속적인 이동을 구분하고, 출발 전 진동 수준 및 시간에 따른 변화 추세를 함께 보도록 개선했다.
- 정지 판정과 ±3 cm 도킹 정확도 판정은 별개로 유지해야 한다.

5-5. 보정 절차가 지나치게 복잡하고 반복 실패
- 수동 직진 보정에서 충분히 이동했는데도 재측정 요구가 발생했다.
- 이후 사용자가 요청한 절차로 변경했다: 센서 준비 → Enter → 정지 30초 → CAN 전진 3초 → 정지·되튐 확인 → 저장.
- 사용자가 수동으로 출발 위치로 돌아온 뒤 별도로 주행을 시작하는 구조다.

5-6. 전진 후 SETTLE에서 즉시 종료
- 전진 3초는 완료했지만 직진 보정 센서/추적 유효성 상실 오류로 종료됐다.
- 정지 후 잠깐 추적이 흔들려도 바로 실패시키는 처리가 있었다.
- 정지 명령을 유지한 채 추적 회복과 연속 안정 관측을 기다리도록 변경했다. 자동으로 다시 전진하지 않도록 했다.

5-7. 마지막으로 확인된 미해결 보정 실패
- BASELINE 중 relative_pose_discontinuity가 여러 번 발생했다.
- 30초 후 시작 정지 관측 부족; 자동 전진하지 않습니다로 종료됐다.
- 이 경우는 전진 중 실패가 아니라 출발 전 정지 관측 단계에서 막힌 것이다.
- 추적 기준이 반복해서 끊기면서 정지 관측 조건을 충족하지 못했다. 허용치만 넓힌다고 원인이 해결됐다고 볼 수 없다.

6. 프로그램 자료형 및 프로세스 처리

6-1. JSON 저장 오류
- recording_io_error: Object of type bool_ is not JSON serializable.
- NumPy bool_ 자료형을 그대로 JSON에 넣어 기록 단계에서 전체 실행이 종료됐다.
- NumPy 스칼라와 배열을 Python 기본 자료형으로 변환하는 처리가 필요했다.

6-2. IMU 공유 메모리 접근 충돌
- calibration IMU snapshot unavailable 오류가 전진 중 발생했다.
- 다른 프로세스가 공유 데이터를 잠시 사용 중이라 non-blocking lock 획득이 실패한 것을 즉시 치명적 오류로 처리했다.
- 직전의 유효하고 신선한 스냅샷을 재사용하고, 실제 오래된 데이터나 센서 오류와 구분하도록 변경했다.

6-3. 반복 stop 요청의 잠금 충돌
- 센서 시작 대기 중 command=stop인데 CAN latched=true로 종료되는 사례가 있었다.
- 이미 정지 상태인 상황의 잠깐 잠금 충돌까지 비상 정지 실패로 처리하는 문제가 있었다.
- 반복 정지 요청과 움직이는 중 새로 들어온 정지 요청을 구분하도록 수정했다.

7. CAN 설치와 통신

7-1. Kvaser 네이티브 라이브러리 누락
- libcanlib.so: cannot open shared object file.
- Python canlib만으로는 충분하지 않았고 LinuxCAN 네이티브 라이브러리가 필요했다.
- 초기에는 자식 프로세스 실패가 _queue.Empty로 나타나 원인이 더 불명확했다.
- 설치 후 /lib/libcanlib.so와 libcanlib.so.1을 확인했다.

7-2. CAN 채널 수 0
- 라이브러리 설치 후에도 getNumberOfChannels()가 0이었다.
- USB 장치·드라이버 연결 확인이 별도로 필요했다. 이후 사용자가 연결 완료를 확인했다.
- 모듈 서명 경고/taint 메시지 자체가 드라이버 로드 실패를 의미하지는 않는다.

7-3. CAN 초기화 Timeout occurred (-7)
- Can 초기화 중 타임아웃이 발생했다.
- 당시 로그만으로 정확히 어느 초기화 호출이 실패했는지 확인하기 어려웠다.
- 실패 단계 표시와 기존 v4 초기 전송·동기화 흐름 비교가 필요했다.

7-4. 실제 CAN ERROR_FRAME 수신
- 전진 중 CAN can_error_frame flags=0x20 오류가 발생했다.
- 해당 로그에서 ERROR_FRAME은 확인됐고 RX overrun은 false였다.
- tx/rx/overrun 카운터가 0이어도 관측된 error frame 자체를 없었던 일로 볼 수는 없다.
- 에러 프레임의 id/data를 일반 차량 메시지처럼 해석할 수 없다.
- 배선, 종단, 차량 측 상태 등 물리적인 발생 원인은 확정하지 못했다.

7-5. CAN 감시 정책과 v4 차이
- v6는 송신 확인, 수신 오류, watchdog 등을 검사해 이전보다 쉽게 실행을 중단했다.
- 사용자 요청으로 v4의 송신 순서·반복 전송·writeSync 동작을 비교해 반영했다.
- 단독 ERROR_FRAME은 기록하는 정책으로 바꿨지만 bus-off, 수신 overrun, 송신 지연 등은 별도로 감시했다.
- 프로그램이 더 이상 같은 예외로 종료하지 않는 것과 실제 CAN 오류 원인이 해결된 것은 다르다.

8. 오류처럼 보였지만 구분해야 하는 현상

- camera fps가 점차 증가: 시작 대기 시간을 포함한 누적 평균이면 처음에는 낮고 시간이 지나며 올라갈 수 있다. 카메라 속도가 계속 가속된다는 뜻은 아니다.
- 카메라 fps와 처리 fps 차이: 수신 프레임 수와 실제 처리된 출력 수는 다르다. 최신 프레임 사용, 처리 비용, 출력 주기가 영향을 줄 수 있으므로 차이를 모두 USB 누락이나 CPU 부족으로 단정할 수 없다.
- odom=true: 유효한 추정 출력이 있다는 뜻이지 실제 위치가 ±3 cm 이내라는 보장은 아니다.
- tag accepted: 검출 수락이지 장착 보정과 차량 위치가 정확하다는 보장은 아니다.
- 테스트 OK 및 빌드 성공: 소프트웨어 검사 통과이며 실제 센서·CAN·차량 주행 검증을 대체하지 않는다.
- 당시 약 48도, CPU 유휴 비율이 높은 로그만으로 과열이나 CPU 포화가 전체 오류의 원인이라고 볼 근거는 없다.

9. 최종 확인 상태

확인된 것:
- 필요한 주요 Python/ROS 패키지 import 및 브리지 빌드 성공.
- 카메라 실시간 영상과 태그 관측 출력.
- OpenVINS odom=true가 지속되는 측정 구간.
- CAN 보정용 전진과 정지 단계 실행.

아직 완료를 확인하지 못한 것:
- 마지막 환경에서 추적 불연속 없이 초기 직진 보정을 끝내고 새 mount를 저장하는 과정.
- CAN error frame의 물리적 원인 제거.
- 전체 자동 도킹 성공 및 실제 포크 끝 위치·각도 정확도 검증.
- 기존 버전보다 정확해졌다는 실측 비교.

보고용 짧은 요약:
이번 실험에서는 RGB·IR·IMU를 결합한 위치 추정 기능을 추가하는 과정에서 설치 환경, 센서 시간 동기화, 좌표계 및 초기 보정 문제가 연속적으로 발생했습니다. 카메라와 OpenVINS의 정상 출력, CAN을 이용한 짧은 전진까지는 확인했으나, 추적 불연속과 보정 조건 미충족으로 초기 보정 완료 및 본 주행 단계 진입이 지연됐습니다. 추가로 CAN 오류 프레임이 관측돼 기존 통신 방식과 비교·수정했으며, 전체 자동 도킹과 정밀도 개선은 아직 실측 검증이 필요합니다.
